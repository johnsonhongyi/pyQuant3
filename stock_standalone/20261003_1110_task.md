# 2026-10-03 11:10 OpenAI Codex 上下文压缩参数优化与 body_after_prefix 性能平衡闭环报告

## 1. 任务背景与核心痛点

用户反馈在日常工程交互中：
- Codex 配置为 `model = "gpt-6.1-sol"`, `model_auto_compact_token_limit = 160000`, `tool_output_token_limit = 10000`, `project_doc_max_bytes = 65536`；
- 痛点问题：“总是显示在压缩 (Compacting session...)”，长对话中频繁被打断卡顿，不仅消耗多余的摘要生成 Token，还容易导致细粒度代码记忆丢失；
- 询问：`model_auto_compact_token_limit_scope = "body_after_prefix"` 是否需要？能否达到更好的省 Token 与性能平衡？

---

## 2. 深度排查与根因确证 (Root Cause)

1. **物理窗口 vs 压缩阈值严重失配**：
   - 排查本地 `~/.codex/models_cache.json` 发现，`gpt-6.1-sol` 真实物理窗口高达 **272,000 Tokens (272k)**；
   - 原配置 `model_auto_compact_token_limit = 160000` (160k) 仅占 58%，白白闲置了 112k 的可用原生空间；
2. **静态前缀 (Prefix) 无辜吃掉配额**：
   - 实测首轮会话数据（`rollout-2026-10-03T10-17-07-01a0ff8d`）：首轮尚未进行深入对话，静态前缀（系统指令 + 工具 Schema + 64KB 项目文档）已经常驻占用了 **30,106 Tokens**；
   - 在默认的 `scope = "total"` 下，前缀算入 160k 阈值，导致留给动态问答和代码输出的净空间仅剩 120k 左右；
3. **真实会话历史压缩频次证实**：
   - 会话 `rollout-2026-10-01T13-24-22` (442 轮)：压缩了 **6 次**；
   - 会话 `rollout-2026-09-30T23-22-49` (352 轮)：压缩了 **5 次**；
   - 某 114 轮会话：压缩了 **4 次**（平均每 28 轮被迫卡顿一次）。

---

## 3. 优化方案实施与配置落地

已在 [`~/.codex/config.toml`](file:///C:/Users/Johnson/.codex/config.toml) 落地黄金平衡配置：

```toml
model = "gpt-6.1-sol"
model_reasoning_effort = "low"

# 1. 显式声明 gpt-6.1-sol 原生物理窗口 (272k)
model_context_window = 272000

# 2. 核心突破：统计范围剥离静态前缀，仅考核动态对话正文 (净增 35,000+ Tokens 工作区间)
model_auto_compact_token_limit_scope = "body_after_prefix"

# 3. 压缩阈值设为 170k (正文达 170k 才压缩，总上下文约 205k，留足 67k 缓冲防溢出)
model_auto_compact_token_limit = 170000

# 4. 单次工具输出上限优化至 8000 (约 700 行代码，防止单次暴饮暴食)
tool_output_token_limit = 8000

# 5. 项目文档上限从 64KB 优化至 32KB (直接省出 12,000+ Tokens 永久常驻内存)
project_doc_max_bytes = 32768
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md", "AGENTS.md"]

approval_policy = "on-request"
approvals_reviewer = "auto_review"
sandbox_mode = "workspace-write"
```
