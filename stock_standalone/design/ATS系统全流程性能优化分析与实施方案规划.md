### 1. 瓶颈一：IPC 重复复制、基线并发与发布所有权
- **事实定位**：
  - `ats/ipc_bridge.py` 的 `_handle_client`：网络接收后台线程解包后执行 `df_norm = df_payload.copy()` 进行差分合并，完成后执行 `df_to_deliver = self._cached_df.copy()` 复制全量表，成本随行列数增长；
  - 同方法调用 `data_callback(df_to_deliver)`，经主窗口信号进入 `_handle_realtime_data`；正常路径是裸 DataFrame，主线程走全量分支。重复复制与索引规整成立，**每帧二次差分合并不成立**，diff 分支是待审计的兼容路径；
  - `IPCBridge.start_realtime_listener` 按连接创建线程，共享 `_cached_df`；全量路径发布缓存对象本身，后续差分可能原位写它，直接删除 UI 防御性复制存在一致性风险。
- **待测影响**：复制字节率、归并耗时与对象驻留。30~80ms、数十 MB/s 尚未采样，不能直接归因为 Minor GC。

### 2. 瓶颈二：通达信 (pytdx) 单一长连接与全局互斥锁串行争抢
- **事实定位**：
  - `ats/tdx_realtime_fetcher.py` 的 `TDXRealtimeFetcher` 共享 API 连接通过 `with self._conn_lock:` 串行保护请求；
  - 虽然 SBC 图表实现了 `SBCGlobalDispatcher`，但新股雷达（`NewStockFetcher`）、涨停天梯（`LimitUpEngine`）、板块矿工（`SectorRotationPullbackMiner`）等仍在各自线程直调 TDX API；
- **待测影响**：锁内网络请求会拖延共享连接消费者；只有确认主线程同步等待或计算阻塞，才能判定 GUI 假死，数据停更需单独计量。统一单线程后仍有调度排队和慢请求队首阻塞。

### 3. 瓶颈三：Qt 表格全量属性更新、排序及布局成本
- **事实定位**：
  - `ats/ui/swing_table.py` 表格更新遍历全表，逐个设置 `QTableWidgetItem` 属性；
  - 同文件 `_apply_favorite_filter` 对每行调用 `setRowHidden`，存在重复布局成本，实际重排次数待测；
  - `ats/ui/ipo_command_room_dialog.py` 的 `refresh_data` 重设行数并构建单元格 item，存在对象分配与布局成本；
- **待测影响**：Qt Widgets 不使用 DOM；已存在 item 复用，主要需量化无变化属性更新、排序、行隐藏和布局成本。25~35 行取决于窗口与 DPI，50~120ms 未实测，屏外数据仍须参与排序、过滤和导出。

### 4. 瓶颈四：计算密集型策略对 Python GIL 的挤占与主线程响应延迟
- **事实定位**：
  - `LedgerUpdateWorker.run()` 承担了 MA20 通道几何测算、资金主线分析、全表均线循环构建等大量纯 Python 运算；
- **待测影响**：纯 Python 工作可能挤占 GIL，但向量化/native 工作不能一概而论；需区分 CPU 时间、I/O 等待和 GUI 线程直接计算。Worker 还调用账本更新、投影同步及文件快照，并非可以随意取消的纯函数。

### 5. 瓶颈五：散弹式历史/价格补齐与磁盘锁争抢
- **事实定位**：
  - `ats/ui/main_window.py` 的 `_flush_batch_stock_prices` 已有防抖合批，但每批新建线程；取得 `hdf5_history_lock` 后才调用新浪 HTTP，网络耗时被纳入锁持有期。超时后标记失败，不应未经核对重试策略就断言循环重试。
  - 拆锁前须审计 `Sina(readonly=True)` 的内部缓存与 HDF5 访问；不能直接将现有锁删除。

### 6. 瓶颈六：次日候选池、配置及历史链路的微观计算与并发瓶颈
- **事实定位**：
  - **宽表重复投影**：_candidate_row_lookup 先复制选列、规范化并筛选候选，最后才 iterrows；历史循环逐候选调用造成重复 O(KN) 扫描。不能据此声称每次 iterrows 都遍历 5000 行或已确认 GC 停顿，行列数、对象分配及耗时待测；
  - **历史文件重复扫描**：_poll_next_day_watch_tdx 启动 Worker 前同步枚举/读取历史文件；run_cycle 内的扫描随调用线程执行，ATS 评估路径在后台。两处均需收敛扫描，不能统称全在 GUI；
  - **重复列宽计算**：后验、检查点、统计及顺延表存在 resizeColumnsToContents 调用，可能重复测量并改变用户列宽；扫描范围受 header 精度、代理和重载影响，非必然遍历所有行，耗时需分表测量。[Qt resizeContentsPrecision](https://doc.qt.io/qt-6/qheaderview.html#resizeContentsPrecision)
  - **Windows 替换与读改写风险**：候选池 _atomic_json 使用同目录临时文件后 os.replace；进程内 RLock 不提供跨进程事务互斥，某些共享模式的句柄会妨碍替换。互斥、重试和版本恢复是独立契约，见 §6.4；
  - **配置同步等待**：load_config_node 一条五次退避路径累计 sleep 为 450ms，仅为分支等待和，不是总耗时上限。save_config_nodes 还含跨进程锁、替换重试和磁盘 I/O；应复用已有机制并移出 GUI，实测尾延迟，不能推断必然出现系统未响应；
  - **信号交付未闭环与伪确认隐患**：`_poll_next_day_watch_tdx:5617` 在 `self.realtime_signal_signal.emit(signal)` 发射信号后，立即调用 `mark_events_delivered` 落盘标记已投递。Qt QueuedConnection 的事件入队不等于消费端（交易账本/报警总线）持久入库成功，若后续消费异常或进程崩溃，事件在源端已记为已交付，彻底丧失补发机会。
- **待测影响**：对象分配、I/O 字节率、锁等待、GUI 长任务与业务数据年龄。优化收益需同负载验证，不承诺一个数量级。

### 1. 加载异步化重构（Async Architecture）
- **主线程热路径无同步 I/O**：接收、唯一归并、纯计算和 GUI 投影分责；不把所有重计算搬进 Socket 接收线程。GUI 仍负责模型提交、布局与绘制，完整回调不能用指针赋值耗时代替；
- **策略计算隔离评估**：先减少重复工作与 Python 对象展开；独立进程只接纯计算，实测覆盖启动/序列化/回传成本后再准入，共享内存另行评估；
- **常驻 Worker 与代际守卫**：每类可合并工作采用一个运行任务加一个最新待处理槽；结果携带版本。账本与信号事件保序处理，不能使用全局 Drop-on-Busy。

### 2. 数据读取全流程优化（Data Ingestion Pipeline）
- **发布隔离契约**：单写者更新私有工作版本，发布版本在所有读者释放前不得修改；先保留必要的隔离复制，再测量减少冗余复制。Pandas CoW 不等于线程同步，也不能靠版本标签冻结对象；
- **统一数据调度**：复用 SBC 已有机制，增加请求合并、容量、截止时间、优先级老化与失败退避；避免重新制造一条无界慢任务队列；
- **分层缓存**：复用 `TDXGlobalCachePool`、已有 RamDisk 与磁盘缓存，增加版本/交易日失效及字节上限；不默认新增 Feather/Arrow 或持久化系统。

### 3. 分段式优化架构（Segmented Optimization）
- **渲染分段**：先脏单元格、样式复用及隐藏页按需刷新；仍超预算的单表再迁移 `QAbstractTableModel + QTableView`，可见范围由实际布局决定；
- **行过滤分段**：使用全数据排序/过滤映射，按稳定证券标识恢复选中和滚动锚点；未变化过滤条件不重复设置行隐藏；
- **计算分段（三级梯度）**：
  - Tier 1（候选 P95 <3ms）：动态报价投影与依赖列变化触发的向量运算；
  - Tier 2（候选 P95 <15ms）：核心标的计算，风险与状态转换频率保持现有业务语义；
  - Tier 3（候选 P95 <80ms）：允许低频的全景统计，周期通过时效契约确定；
- **传输分段（后期候选）**：先列裁剪与订阅合并，再考虑双轨。5000 行 × 6 个 float64 字段已有 240000 字节，未计索引和协议头，不能承诺全市场 <15KB；`vwap/rank` 并非静态字段。

## 三、分阶段实施演进路线图（Stage 0 至 Stage 5）

> [!NOTE]
> 实施路线严格遵循“基线先行、热点分离、逐步推进、指标量化”的准入驱动原则。

| 阶段 | 阶段名称 | 核心改造范围 | 准入门禁与可衡量预期成果 |
| :--- | :--- | :--- | :--- |
| **Stage 0** | **基线、契约与黄金样本** | 复用 `ats/startup_profiler.py`，加入候选池加载/评估/确认与文件写者清单 | 记录调用线程、文件数/字节/检查点数、锁等待、源数据年龄和输出真值；所有预算经基线校准 |
| **Stage 1** | **唯一归并、快照隔离与协议保真** | IPC 信封；候选池文件所有权、事件提交确认、配置版本 | 跨日/缺包/空值/慢读者与多进程写入、重试不丢不重验证通过；摄入 P95 <2ms 为候选目标 |
| **Stage 2** | **有界调度与缓存治理** | SBC/TDX 复用；候选池 Loader、配置/板块/HDF 后台读取 | GUI 无同步业务文件/网络 I/O；一项任务在途加一个最新展示请求槽，业务请求独立保序；关键请求满足截止时间 |
| **Stage 3** | **纯计算与业务提交分离** | 各引擎、候选池历史行查找/检查点持久化、纸面账户读投影 | 一版输入复用一版结果，过期输出不污染业务状态；写放大有界且持久性不退化；按热点决定是否进程化 |
| **Stage 4** | **表格增量更新与按需模型迁移** | 原有三表、候选总览/后验/统计/顺延表、动态列布局 | 全数据排序、选择、过滤、导出及策略复合身份保真；增量更新 P95 <3ms 为候选目标 |
| **Stage 5** | **故障注入、退出与长周期验证** | 现有影子工具适配性核验；回放/监测能力待规划 | 先短回放再 4h/72h，记录内存斜率、句柄与任务数；不得声称有限压测证明零泄漏 |

依赖：Stage 0 是全部实施的前提，Stage 1 先于共享快照优化；Stage 2/3/4 可按基线热点分支推进，不强制串行大改。启动优化在 Stage 0 测量、Stage 2/3 落地，退出契约随资源引入同步设计，最终由 Stage 5 验证；本轮所有 Stage 均未实施。


## 六、数据与并发契约：极限优化前的必要条件

### 6.1 IPC 顺序、ACK 与空值保真

1. **逻辑单写者**：接收线程不直接写共享基线；唯一归并者按发送端定义的顺序接受更新，不能拿连接完成顺序代替行情顺序。先复用现有 `source_version/sync_session`，审计其递增含义后再决定是否扩展 `base_version/schema_version/trading_day`。
2. **版本有效性**：会话变化、跨日、基线缺失、重复、乱序、结构变化分别定义处理；若 source_version 允许跳号，用显式基线关系校验，不能简单把非连续整数判成丢包。无法验证依赖链则限频请求 full，并保留最后可信快照及 stale 标记。
3. **接受后确认**：ACK 表示包已校验并有序归并、可供恢复/发布的版本已被接受，不表示 GUI 已显示或业务已提交。失败包不得伪成功 ACK；若现有生产端确认语义不同，先双端兼容迁移与重放验证，再改变确认时点。
4. **空值与删除**：当前 `notna()` 合并不能表达“将旧值清空”；复用发送端空值逆转、行列结构变化回退 full 的契约，不先修改一端。显式空值掩码、删除标记仅作为协议升级候选；证券标识须含市场语义，不能把指数和同号个股压成同一个键。
5. **收包边界**：固定长度头需完整读取；包体设字节上限、累计超时与最大同时在途容量。先归并 diff 才能合并展示通知，不能在网络输入阶段任意丢弃增量。

### 6.2 快照生命周期与有界邮箱

- **第一阶段保守隔离**：生产者拥有可变工作版本，发布独立快照；只删除已证明冗余的复制。标签、浅复制和 GIL 均不能替代发布后不再写入的契约；object 列中的嵌套可变对象也需规整或隔离。
- **第二阶段按需减少复制**：热数值列投影、静态列按版本复用；只有写路径与读者生命周期全部明确后，再评估块级复制或缓冲池。Pandas CoW 版本/配置需记录，不能作为无条件线程安全依据。[Pandas copy 文档](https://pandas.pydata.org/docs/reference/api/pandas.DataFrame.copy.html)
- **UI 邮箱**：最多一个待消费展示快照、一个待处理通知；消费者读取最新版本后，受同步保护地清理/重新检查通知标记，防止生产者恰好写入导致丢唤醒。仅在 GUI slot 丢旧帧仍无法阻止 Qt 事件队列积压。
- **计算邮箱**：一个运行任务加一个最新待处理请求；过期纯计算可在安全点取消，但设置完成/发布时间上限，防止行情持续到达导致永远取消。全局市场帧、窗口代码/周期、策略配置、交易日分别带代际，结果匹配相应依赖后才提交。
- **读者回收**：计算完成、取消、异常、窗口关闭均释放快照引用；固定池满时合并展示需求或受控回压，不能覆盖仍被读取的缓冲，也不能无限创建新版本。

### 6.3 展示快照与业务事件分流

| 数据类别 | 可否 latest-only | 顺序和溢出策略 |
| :--- | :--- | :--- |
| 单元格当前报价、直方图展示 | 可以，须保留最后可信时间和版本 | 覆盖待显示槽，监测快照年龄；diff 输入先归并 |
| 无副作用的全景统计请求 | 有条件可以 | 明确依赖版本和最长完成时间；结果不直接改账本 |
| 突破/回落状态、峰值、累计量、告警触发 | 默认不可以 | 可能依赖中间路径，保序计算或保真聚合，不能仅看末帧 |
| 交易事件、账本迁移、持仓核对 | 不可以 | 唯一所有者提交、事件 ID 幂等；沿用原有持久化语义，有界满载时回压或可恢复溢写并明确失败状态 |

- 现有 Worker 已写账本，后续设计须先明确“计算→校验→提交”边界；可取消部分不接收可变 ledger、QObject、数据库连接或锁对象。
- 即便当前业务路径本身已跳帧，新方案也需对齐相同输入与时序基线；改变策略采样频率属于语义变化，不能用性能优化默认授权。

### 6.4 跨进程文件写入与 Windows 文件锁安全契约

1. **写者所有权清晰划分**：
   - 盘前候选冻结清单（`watch_*.json`）：TK 与 GUI 补算必须经同一写者入口，或持跨进程锁重新读取、校验并提交；“TK 或 GUI”不是互斥机制；
   - 盘中实时后验与统计（`eval_*.json`, `stats_*.json`）：由 ATS 实时评估 Worker 作为主写者负责维护；
   - 配置文件（`next_day_watch_strategies.json`, `window_config.json`）：由配置管理器通过后台串行持久化队列写入。
2. **Windows `os.replace` 的 `WinError 32` 容灾模式**：
   - 是否冲突取决于句柄共享模式等条件，不能声称所有打开的读句柄都会阻止替换；共享冲突与权限不足、磁盘故障分别处理。[Microsoft 文件共享模式](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea)
   - 重试仅对可恢复的共享冲突生效，在后台执行并限制总截止时间；10/20/40ms 加抖动只是待测候选参数。应用写者互斥防丢更新，替换重试应对临时占用，两者不能互相替代；完整读改写事务纳入同一锁/版本校验。
   - 失败临时文件不能在下一轮直接覆盖正式文件。可重建快照可清理后重算；业务提交依靠持久待办恢复，需保留的临时产物进入有容量/期限的隔离区，带目标路径、基线版本、校验和及事件 ID；恢复前锁内校验当前版本，过期产物拒绝回写，禁止仅按 mtime 选最新文件。
   - 读端使用上下文管理及时关闭句柄；磁盘满、权限错误等明确反馈，重试耗尽保留上一份可信正式文件。Windows 文件占用测试必须实际创建不允许删除共享的句柄，不以普通 open 必然冲突为前提。

### 6.5 业务事件持久待发、至少一次投递与消费提交确认

本协议没有分布式 prepare/commit，不称为 2PC。目标是可恢复的至少一次投递，业务效果只执行一次依赖消费端将 event_id 去重记录与业务更新原子提交；现有存储能否提供该事务边界须先审计。

```mermaid
sequenceDiagram
    participant Engine as 候选池后验引擎 (Worker)
    participant Storage as 磁盘持久化 (eval JSON)
    participant Bus as 信号派发总线 (Qt Signal)
    participant Consumer as 消费端 (交易账本/报警总线)

    Engine->>Storage: 1. 发现确认事件，持久化写入 PENDING_DELIVERY (含 event_id)
    Engine->>Bus: 2. emit 实时信号广播 (含 event_id)
    Bus->>Consumer: 3. Qt QueuedConnection 派发事件
    Consumer->>Consumer: 4. 本地持久化事务入库 (基于 event_id 幂等去重)
    Consumer-->>Engine: 5. 回传 EVENT_ACK (event_id, ack_time)
    Engine->>Storage: 6. 原子翻转 delivered = True 并持久化
    Note over Engine,Consumer: 未收到 ACK 时有界退避重发；消费者查询持久提交记录后回复重复 ACK
```

1. **废除伪交付**：彻底废除 `emit` 信号后立即在源端标记 `delivered = True` 的假交付逻辑；
2. **状态演进闭环**：事件生命周期严格演进：`PENDING_DELIVERY -> DISPATCHED -> COMMITTED -> DELIVERED`；
3. **事务 ACK 回传**：消费端只在相应持久业务提交成功后确认；内存报警队列接纳不等于落盘，多消费者分别定义必须确认者。ACK 携带 event_id、消费者身份、业务版本和提交结果；业务更新与去重记录无法原子提交时，先补可恢复提交日志，不承诺效果恰好一次。
4. **恢复与终止条件**：源端待发清单独立于新一轮行情评估恢复，停盘/跨日也能完成交付处理；重试总在途数、速率和年龄有界。确认时间与投递重试时间分离，不能把两帧证明的时间窗直接当 ACK 超时；按原始事件时间校验，过期/非法事件持久拒绝并留原因，不能跨日无限重发或重新当日触发。
5. **崩溃窗口验收**：覆盖源端待发落盘前/后、消费业务提交前/后、ACK 发送前/后及 delivered 写入前/后的进程终止；重启读取持久幂等结果。去重保留期覆盖最大重试/恢复期，未完成事件不得被历史剪枝清理。

## 七、各层可继续补充的优化方案

### 7.1 TDX/HTTP 调度：消重优先于扩容

- **请求键**：`来源 + 市场/代码 + 数据类型/周期 + 范围 + 复权口径 + 交易日/代际`；相同键的在途请求合并为一次拉取、多订阅者分发，force 请求必须受配额和合并规则约束。
- **优先级**：P0 持仓风险与关键业务，P1 激活视口与交互，P2 历史回填和全景；隐藏窗口只降低展示订阅，不能关闭风险计算。低优先级使用等待时间提权或配额保证，防止长期饿死。
- **容量与截止时间**：分别限制等待任务数、合并键数、订阅者数、在途请求和字节；入队前淘汰已过期的可替代请求。运行中的阻塞网络调用通常不能被新高优先级任务抢占，需传输超时和批次间让出。
- **故障隔离**：先单连接所有者加慢任务分段；若关键数据仍被历史回填拖延，再评估至多两个独立连接通道，各自独占 API 实例，并控制总请求速率。不能让多个 Worker 并发使用同一个 pytdx 连接。
- **恢复**：超时使用有上限的退避与抖动、熔断和少量探测请求；返回缓存时附数据年龄/失败原因，风险消费者按业务最大年龄拒绝不可信数据。取消订阅后没有消费者的等待任务可撤销，在途结果不再触碰已关闭对象。

### 7.2 数据读取、缓存与持久化

- **不建第二套缓存**：复用 TDXGlobalCachePool、历史缓存及现有代际失效；记录命中/过期/负缓存命中、重复拉取与每类字节占用。TTL 不替代数据版本，跨日、复权、配置变更、数据修订、停复牌均纳入失效表。
- **负缓存**：区分成功空结果、未上市/停牌、网络失败和非法请求；失败短冷却并退避，成功空结果可按交易时段复用，避免空集每帧重算。行情恢复或交易日切换必须解除旧失败状态。
- **最小读取**：历史数据按证券、日期范围和必需列读取，批量合并区间；缓存规范化代码及静态名称。SQL 索引和投影优化必须基于真实查询计划，不能凭列名盲目加索引。
- **锁粒度**：为价格补齐、历史读取、序列化与提交分别记录锁时间；在确认底层副作用后将纯网络等待移出磁盘临界区。跨线程/跨进程连接和 HDF 句柄归属明确；不假定 HDF5 可安全并行写，也不为提速降低既有数据库持久性。
- **写入分级**：可重建历史统计批量写，业务事件保持必要确认；临时文件与目标同目录、关闭句柄后原子替换，Windows 文件占用需有限重试和保留上一版。遥测日志异步合批、采样和轮转，防止优化探针成为新 I/O 热点。

### 7.3 增量计算与共享结果工厂

- **依赖表先行**：按引擎声明输入列、历史窗口、交易日、配置与输出；行情、均线、板块映射只规整一次，同版本 `CapitalDragonEngine`/`LimitUpEngine` 报告供 Worker、主面板和弹窗复用。已有 1s/1.5s 缓存保留为保护，增加版本有效性。
- **按脏依赖重算**：价格变化只更新依赖价格的指标；历史 MA/通道等在 bar 完成、修订或配置变化时失效。板块聚合需维护旧贡献减去、新贡献加入，成员迁移/空值/修订触发正确失效；全市场排名不得只重算当前可见行。
- **减少 Python 展开**：`target_df.to_dict('index')` 已是候选子集，先裁剪实际需要的列，再比较数组/元组投影；滚动和/极值增量化须覆盖当前未完成 bar、重复更新、回补修订与数值误差，不贸然降低浮点精度。
- **状态计算保真**：阈值穿越、告警、累计量与风险计算保留时间序列语义；纯展示统计才可降频。主线程现有 `pd.cut` 和天梯扫描移入纯计算结果生产侧，`QTimer.singleShot` 仅用于轻量提交。[Qt 定时器文档](https://doc.qt.io/qt-6/qtimer.html)
- **进程准入**：测量 `T打包 + T传输 + T计算 + T回传 + T提交` 是否低于现状且改善 GUI P99；先一条常驻纯计算进程，避免多个重型实例和 BLAS 线程过量竞争。Windows 使用可导入顶层入口与 spawn 兼容设计，已有 `run_ats.py` 的 `freeze_support` 要复用并验证打包入口。[Python multiprocessing](https://docs.python.org/3/library/multiprocessing.html)
- **共享内存后置**：仅适用于传输已成为主耗时的数值块；生产者填充、版本提交、读者租约及释放分别定义，不在共享区放 Python 对象指针。Windows 必须关闭所有句柄后才能回收映射；取消、子进程崩溃、退出均覆盖，不以“零序列化”承诺零成本。[Python SharedMemory](https://docs.python.org/3/library/multiprocessing.shared_memory.html)

### 7.4 UI：增量投影、模型线程和真实绘制

- **渐进顺序**：现有 item 原位复用 → 值/颜色/字体/提示内容未变则跳过 → 过滤/排序结果复用 → 热点单表 Model/View。不要把数百行直接认定为必须自建虚拟滚动器。
- **排序与身份**：保存当前排序字段/方向，按稳定证券键恢复选中、编辑、上下文菜单和滚动锚点；排序映射覆盖全部行，复制/导出不能只导出视口。区分“全局过滤后的行映射”和“屏幕可见范围”。
- **模型线程**：Worker 产出普通数据，GUI 线程执行 model 数据变更和 `dataChanged`/行增删/布局通知；后台不能直接操作 QAbstractItemModel。避免每帧 resetModel，必要 reset 时显式恢复状态。[Qt 模型线程要求](https://doc.qt.io/qt-6/qabstractitemmodel.html#thread-safety)
- **布局成本**：仅结构/可见性改变时处理隐藏、行高和列宽；固定样式对象复用，Tooltip 等低频内容按需产生。QTableView 按需取数不代表其排序/布局天然只消耗可见行成本。
- **交互优先**：拖拽缩放期间合并装饰更新，业务数据处理持续运行；隐藏页只保留最新版本，重新显示时一次补齐。统计更新调用与 paint 的实际耗时，禁止用 `processEvents()` 循环掩盖长任务并引入重入。

### 7.5 启动加载与退出闭环

- **启动依赖图**：运行时/导入 → QApplication/最小窗口 → IPC 接入 → 可信基线 → 必需账本恢复 → 当前页 → 历史预热/其他窗口。只并发独立的 I/O 工作，QWidget 创建留在 GUI 线程；业务状态未就绪时不发布可操作的“已就绪”状态。
- **四个里程碑**：进程开始、首个可交互窗口、首个可信行情、关键业务状态就绪；冷启动与热启动分别采样，含 TK 不在线、缓存不存在和磁盘慢场景。复用 StartupProfiler，但补齐导入前的计时覆盖，不能仅统计 `window.show()`。
- **配置/文件检测**：构造器及其依赖项逐项审计 I/O；重复配置读取合并，文件变化检测后台化。数据库若采用 WAL，主文件 mtime 不是可靠的全部变更指示，评估同连接 `PRAGMA data_version` 或业务版本契约，先验证实际存储模式。
- **有序退出**：停止接新任务 → 停止定时器/订阅 → 取消可重建工作 → 有期限地完成业务写入 → 回收网络/线程/进程/共享内存 → 退出。主线程不做无限 join；处理晚到信号和已删除窗口，必要未完成业务状态显式留痕，不依赖 `os._exit` 后的清理钩子。

### 7.6 次日候选池专项：加载、评估与事件闭环

**边界**：嵌入页、独立弹窗和独立进程可以展示同一来源；候选冻结、盘中后验和顺延追踪仍是业务流程。隐藏窗口只能暂停展示读取/渲染，不能暂停必要评估、证据采集或事件交付。

1. **加载请求有界与生命周期收敛**：每个展示消费者采用一个在途任务和一个最新待处理请求；请求携带窗口 epoch、目标交易日、配置/数据版本，返回时全部匹配才接纳。关闭/换日撤销订阅而非强杀正在写文件的 Worker，finished、error、cancelled 分开处理，回收线程对象并拒绝晚到信号；
2. **完整后台投影与受控发布**：把日期枚举、manifest/eval/stats 读取、顺延汇总和格式计算收敛为后台任务，GUI 只提交投影；按绑定类型核验信号传递的复制/引用行为，不假定 PyQt 信号会自动深拷贝。元组含可变成员也不代表深度不可变；普通值投影发布后不得再修改，并限制在读版本数量。进程内复用同版结果，跨进程先按文件版本失效；
3. **一致读取与版本指纹**：watch/eval/stats 是分别替换的文件，单个 Loader 也可能读到混合代际；增加共同 revision 或提交清单，读前后核验，不一致则有界重试并保留上一份明确标记的快照。旧格式先适配校验日期/配置指纹和来源关系，无法确认时不宣称强一致，禁止忙循环等待写者；
4. **展示按需与失效订阅**：GUI 不读业务文件，外层可见且相关页面激活时请求后台投影；历史日期仍可能因顺延事件、ACK 或补档更新，不能一律禁刷。按来源 revision/文件变化失效并低频兜底；隐藏停止展示订阅，后台业务评估继续；
5. **补算完整后台化**：GUI 仅捕获目标交易日、来源描述和必要快照版本；磁盘宽表定位/读取、交易日查询及输入校验放入 Worker。内存 DataFrame 不能因“传了引用”就视为冻结快照，须沿用 §6.2 所有权契约；板块来源同样绑定 asof，不得使用另一日期缓存补齐；
6. **重复补算合并**：任务键至少包含数据目录、目标交易日、来源版本、配置指纹及操作类型；跨嵌入页/弹窗/独立进程协调执行。保留现有非空冻结清单不可覆盖、EMPTY 可修复的规则，业务写入操作不能简单按最后一次点击覆盖；按钮忙状态在接受任务时生效，失败可重试且不虚报成功；
7. **按路径/版本缓存配置**：后台加载已校验快照，受控写者负责修复/保存；不同配置路径不能混用全局单例。显式保存、文件/目录通知与低频校验共同失效，原子替换后核验 watcher 订阅；通知不能保证无遗漏，历史冻结策略保持原指纹；
8. **历史追踪按冻结契约剪枝**：以历史候选自身冻结的 `followup_trading_days` 与交易日历计算到期日，不能固定近 3 日或仅使用当前配置最大值；历史版本可能有更长窗口。维护活跃追踪、到期未终结及未确认事件三个索引，到期先补现有 MISSED 等终结状态再退出活跃集。已知日期直接构造路径，先 glob 全目录再过滤仍是 O(历史文件数) 的目录扫描；首次后台建索引、低频校验及补到/修订失效作为兜底，失效时显式重建而非漏算；
9. **一次规范化、候选并集投影与查找复用**：目前 iterrows 在候选筛选后执行，反复复制/规范化/筛选宽表才是历史单候选调用的首要优化点；一轮汇总当前和历史候选代码，只转换需要的列与行，比较字典索引和元组/数组投影。固定列数时扫描/查找项可由 O(KN) 走向平均 O(N+K)，列宽、字典构建及内存成本另计；不承诺零对象分配或消除 GC。保留重复代码 keep=last、代码/市场规范、空值与数值类型、动态列及 _row_dict 的业务转换；行缓存按行情/字段版本失效，多策略状态仍独立；
10. **证据与降频分离**：保留 required_fields、proof_any、真实 VWAP 缺失、报价推进两帧确认、确认时间窗、EARLY_VALID 收盘保留及实际交易日顺延。缓存命中不能伪造新行情时间；已有推进规则需逐分支保真，不能将重复读取同一报价计作第二帧。展示只保留最新快照，业务证据序列在准入与过载策略中单独保障；
11. **无变动跳写与审计证据分离**：拟按持久内容维护 eval_changed/stats_changed，覆盖检查点、候选状态、事件/ACK、终结状态和业务时间。现有不同 observed_at 会追加检查点，即使报价没有推进也可能有新证据，所以脏检查本身不能保证大量跳写，更没有“减少 85%+”的实测依据。删除/压缩检查点或改变采样属于独立语义变更；先在证据保真的前提下测量无变化跳写，必要时另行评估增量日志与快照，持久化水位不能被内存刷新时间冒充；
12. **多写者与 Windows 锁防护**：严格划定 TK 冻结、ATS 评估、手动补算、ACK 与配置修复的所有权；按 §6.4 分离事务互斥、临时共享冲突重试和故障恢复，恢复必须校验版本，不能自动推广失败快照；
13. **至少一次投递与持久确认**：遵循 §6.5 的持久待发、消费幂等事务、ACK 与源端确认链路；重试与行情周期解耦，明确拒绝/过期、崩溃恢复和容量门槛，不称为 2PC 或无条件恰好一次；
14. **按结构及用户操作调整列宽**：常态数据刷新避免重复测宽，覆盖事件、检查点、统计和顺延表；首次构建、新列、DPI/字体变化及用户显式适配按需处理，优先保留人工列宽。选择行切换检查点时验证长文本可读性；仍需治理 item 创建、排序及绘制，不能承诺消除全部布局成本。

### 7.7 更新后的板块、布局与账户投影

- **休市板块与期限负缓存**：缺失路径采用可配置短 TTL 加目录变更通知，手动强刷、文件补到及交易日切换使其失效；不能缓存到次日开盘而掩盖盘后补档。区分不存在、损坏、读取失败，短暂错误不记为确定缺失；文件不存在时没有解压成本，收益主要来自避免重复目录扫描和空态重绘，已有文件的解压复用另测；
- **配置持久化有界合并队列**：复用已有防抖及 save_config_nodes 的跨进程锁/替换重试，将最终 I/O 移到后台；以文件路径与键为维度限制待写键数、字节、年龄及在途量，同键仅对可替代布局值保留最后版本。队列满或写失败明确反馈并保留待保存状态，显式策略保存单独有序确认；跨进程在锁内读取最新版后合并，防止旧快照覆盖他人键。现有 Windows 互斥为无限等待，必须规划有截止时间的获取及可取消等待，防止后台队列或退出永久堵塞；GUI 入队仍测 P95/P99，入队不等于保存成功。
- **账户读投影**：从 TK SSOT 获取带权威修订的只读模型，按账户标识、baseline 指纹、订单修订缓存基线归并结果；仅在确认追加时增量重放。订单缩短/历史内容修订、重置、基线变化或解析失败触发完整校验与重建，不能仅以 order_count/mtime 判定相同；保留既有时间戳归一化与账户可用状态；
- **退出覆盖与守护进程清理**：主窗已经停止候选池定时器，但后台 daemon、Loader、FreezeWorker 和配置持久化仍需统一登记与收尾；关闭窗口不能使写入半完成或晚到结果触碰控件。进程级强制退出存在于 `ats/main_ats.py`，所有必要持久化须在此之前获得明确结果。

## 八、结构性能上限与容量模型

没有基线不能报“系统极限 FPS/TPS”。以下模型用来判断优化是否迁移了瓶颈，输入由 Stage 0 实测填入。

| 维度 | 模型 / 测量口径 | 决策意义 |
| :--- | :--- | :--- |
| 端到端时延 | 单帧各阶段排队与服务时间之和，额外记录源数据年龄 | 按 frame_id 关联接收、归并、计算、提交和 paint；各阶段 P99 不能简单相加当总体 P99 |
| 网络容量 | 单通道利用率 `ρ = Σ(请求率_i × 平均服务秒_i)` | `ρ >= 1` 无法长期稳定；Stage 0 后留波动余量，先消重/合批，不能靠调优先级制造吞吐 |
| GUI 预算 | 窗口内 GUI 工作总量 `Σ(触发率_i × 单次 GUI 耗时_i)` | 每个回调都小于 2ms，叠加大量回调仍会卡顿；同时限制通知率和每轮处理预算 |
| 复制/传输 | `动态行数 × 投影列宽 × 帧率 × 复制次数`，另计 object/索引/协议头 | 衡量列裁剪与低复制的真实收益；快轨大小以编码后字节测量 |
| 驻留内存 | 工作基线 + 在读版本 + 待处理槽 + 缓存 + Python/Qt/native 开销 | latest-only 只有在通知和读者数量也有界时才能限制内存 |
| 候选池文件写放大 | n 个候选、q 轮检查点、单点 b 字节，单文件 O(nqb)，逐轮重写累计可达 O(nq²b) | 固定规模简化模型；新增检查点仍须持久化，跳写比例待测，不承诺 85%~95% |
| 历史追踪与宽表查找 | 重复扫描 O(KN)；固定列宽时一次规范化与并集查找可趋向平均 O(N+K) | 计入列宽、构建/失效及内存成本；按冻结期限索引，保留到期结算与未确认事件，不固定 3 日 |
| 表格刷新与几何重排 | 分列测宽、item 更新、排序、布局和 paint，按实际检查行列计量 | 常态跳过无变化工作；用户列宽、动态列和滚动保真，不预报数十毫秒收益 |
| Windows 锁争抢与主线程延迟 | 一条退避分支 sleep 合计 450ms；总耗时含锁、I/O 和其他重试 | GUI 入队、排队、提交和退出 flush 分别测 P95/P99，不承诺 <0.1ms 或 0ms |
| 加速上限 | `S <= 1 / ((1-p) + p/s)`，p 为目标环节的实测耗时比例 | 示例：占比 20% 的环节即使零耗时，总体最多约 1.25 倍；禁止把局部收益当整体收益 |

- **测试规模**：1000/5000/10000 行，按实际字段组成设置窄/宽表；0/1/5/10 个可见窗口，50/300/1000 行表格，1/3/10Hz 回放、1%/10%/100% 变更率；高档为压力场景，不暗示生产源具备此频率。
- **新增负载维度**：候选数、每代码策略版本数、累计检查点数、历史文件数、有效顺延交易日数、同时展示入口数；分别组合空库/长期历史、开盘/收盘、慢盘/文件占用和配置损坏修复。比较单轮时间随全天累积的斜率，不能仅测小文件冷启动；负载只用隔离目录的构造/脱敏回放样本。
- **环境记录**：CPU 核数与频率、电源模式、内存、磁盘/RamDisk、Python/Pandas/Qt 版本、CoW 设置、DPI、打包方式；同环境同输入至少多轮比较，开盘突发与稳态分开报告。
- **采样分层**：轻量计时/计数长期采样，Python 分配与 native/Qt 资源专项采样，避免重型探针对所有帧全开；对比有/无探针开销。CPython 循环 GC 与引用计数并存，数组分配或 RSS 增长本身不证明 GC 卡顿。[Python GC 文档](https://docs.python.org/3/library/gc.html)
- **降级闭环**：依据队列年龄、事件滞后、CPU、内存和数据新鲜度持续越界触发；先暂停预热/装饰，再降低纯全景刷新，保留关键业务。进入与退出使用不同阈值、持续窗口和最小驻留时间，防止反复震荡；恢复时错峰预热，禁止同时补齐所有欠账。

### 9.2 每阶段必须形成的交付物

- Stage 0：环境与负载清单、分位数/尾部样本、输入输出真值、热点排序；增加文件读写者/调用线程矩阵和候选池全天文件增长曲线，无此产物不定性能收益。
- Stage 1：版本/空值/所有权、copy/ACK 对照；验证持久待发与消费事务、跨日重试/拒绝、多写者互斥及版本恢复。
- Stage 2：各 API 请求清单、去重键、容量和截止时间表、缓存失效表；补 Loader 有界/关闭收尾、GUI 无业务 I/O、隐藏页停止展示读取及休市板块期限负缓存。
- Stage 3：指标依赖图、纯计算与唯一提交职责、同版本复用率；补行查找单次字典投影、历史交易日有效剪枝、无变动脏检查跳写证明与账户读模型投影对照。
- Stage 4：表格更新/排序/布局/paint 分解与列宽回归；配置队列容量、故障反馈、入队/提交延迟及退出 flush 实测。
- Stage 5：端到端负载报告、72h 资源趋势、恢复与退出时限、回退演练；不能用单元测试通过代替性能验证。

### 9.3 回退契约

- 每阶段独立开关或适配层，影子路径只计算和对比，不重复写账本、发告警或触发交易副作用；协议升级先具备能力协商，旧发送端/接收端继续使用现有 full/diff 契约。
- 发现状态分歧即停新路径；性能退化按相同负载的 P95/P99、数据年龄和资源水位判断。回退所有权或传输路径时先停止新提交、排空/取消可重建工作、重建可信 full 基线，再恢复单一写者，不能新旧路径同时修改同一状态。
- 不默认引入 Redis、Ray、Dask、GPU、JIT、Arrow、RamDisk 新层或全项目重构；只有现有能力无法达到经确认的预算，才独立评估依赖、打包、运维及收益。
- 若引入候选池新持久化格式，先定义旧读取器兼容投影与可逆迁移；切回前停止新写者、完成必要业务提交并校验导出，不以双写两个权威来源作为常态。durable event/配置冻结/交易日语义不能随着性能开关回退为丢失状态。
