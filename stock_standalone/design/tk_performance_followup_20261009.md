# Tk 主表性能定位与修复记录

> 后续已实施横向可见列裁剪，最新结果见 [列视口优化记录](tk_column_viewport_20261009.md)。本文保留上一轮测量与当时的限制，不代表当前代码仍未实现列裁剪。

## 结论

- 主要问题是多列 Treeview 的同步原生重绘，不是简单的“Tk 放不下 5500 行”。相同视口下 200/5500 行的重绘耗时接近，减少显示列数则明显加快。
- 已精简单元格布局、按列差量写入、合并最新帧、滚动时暂停非关键 UI 写入，并移出点击路径中的策略报告计算及联动进程启动。
- **尚未达到 Qt 竞价面板的流畅程度。** 26 列单次重绘仍约 237 ms；不能把短回调或 `after(16)` 当作 60 FPS 的证明。

## 测量边界

- 基线为不可变提交 `4c108dfc`；优化版为本次工作区代码。Windows、Tk 8.6.12、vista 主题、26 列、每列 64 px、1200×600 视口，约 28 个可见数据行。
- 隔离测试不启动交易程序、不连接行情服务、不执行真实联动或交易。使用实际生产渲染器、标记器和滚轮绑定，AST 加载避免启动副作用。
- 主线程延迟：向测试 Treeview 私有 HWND 投递 `WM_MOUSEWHEEL`，计时从实际投递到首个 Tk 处理器执行；每场景 32 次、目标间隔 16 ms。静态/实时场景的探针不滚动；快速滚轮场景前半向下、后半向上，**32 次均验证视口发生变化**。
- 实时和滚轮场景以独立线程每 100 ms 生成行情快照，GUI 每 10 ms 接收最新版本，刻意绕过主程序刷新限流，属于渲染器压力测试。不是完整实盘负载。
- 原生重绘：单独计时 `yview_scroll`/样式写入调用及紧随其后的 `update_idletasks()`，每组 12 次。后者包括 Tk 空闲绘制和相关布局，不是 Windows DWM 呈现耗时。
- 使用已映射离屏窗口，显式初始化布局及滚动范围；不测物理鼠标到显示器像素的延迟。P95 使用最近秩；12 次样本的 P95 实际为最大值，存在系统调度噪声。
- 初次离屏滚轮测试未初始化滚动范围，出现无实际滚动的极低延迟，**已作废**。旧 JSON 仅 `components` 有效，`scenarios` 不可引用；正式场景结果见 `tk_interaction_scenarios_verified_20261009.json`。

## 字体、图标、列数与原生重绘

单位 ms，P50 / P95。以下是独立组件对照，不使用已作废的旧场景指标。

| 条件 | 200 行：前 → 后 | 5500 行：前 → 后 |
|---|---|---|
| 26 列 ASCII | 345.24/364.89 → 236.12/251.76 | 344.26/413.30 → 238.28/282.82 |
| 26 列中文 | 345.87/391.20 → 236.95/248.61 | 344.71/371.83 → 237.26/282.39 |
| 中文＋Unicode 图标 | 350.76/398.22 → 237.11/261.35 | 352.53/372.81 → 240.83/257.60 |
| 图标＋粗体行标签 | 350.78/385.43 → 247.89/259.12 | 352.79/382.38 → 245.67/270.30 |
| 26 显示列，窗口缩窄到 420 px | 345.86/357.45 → 234.23/284.84 | 347.24/366.75 → 234.52/273.28 |
| 同样 26 数据列，仅显示 6 列，420 px | 80.44/89.64 → 57.61/65.40 | 82.97/96.26 → 56.74/60.78 |

- 简化 `.Cell` 的标准 padding 包装后，26 列中文重绘 P50 降低约 31%。没有移除字体、颜色、图标或真实数据列。
- 图标相对中文增加约 0.2–3.6 ms（优化版 P50），粗体增加约 8.4–10.9 ms；均不足以解释主要卡顿。
- 缩窄窗口几乎不降低 26 列绘制成本，而真正减少 `displaycolumns` 至 6 列降低至约 57 ms，证明不能只依赖窗口裁剪。6 列是实验对照，**生产代码没有自动隐藏列**。
- Tk 8.6.12 的 `DrawCells()` 逐一调用所有 `nDisplayColumns` 的 `DisplayLayout()`，该循环没有按横向视口跳过屏幕外列；与实验一致。[Tk 8.6.12 源码](https://raw.githubusercontent.com/tcltk/tk/core-8-6-12/generic/ttk/ttkTreeview.c)
- 这里的“原生”指 Tk C 层同步绘制，不是 Windows 原生 ListView 控件；证据支持当前 Windows/Tk/主题组合存在重绘瓶颈，不能泛化成所有 Tk 表格必然同样慢。

## 整行、样式和列宽成本

以下为优化版 200 行组件实验，单位 ms，P50 / P95。整行及标签各写 24 行。

| 操作 | Python→Tk 调用 | 随后的空闲重绘 |
|---|---:|---:|
| 重设完整 `values`，即使值相同 | 0.65 / 0.68 | 238.89 / 261.55 |
| 更新整行 tags | 0.20 / 0.36 | 236.65 / 252.80 |
| 相同参数重复 `tag_configure` | 0.03 / 0.03 | 237.13 / 263.74 |
| 26 列重设相同列宽 | 0.15 / 0.18 | 239.74 / 292.46 |

- 这些调用本身很快，触发的绘制很贵。5500 行整行赋值组仍有 336.11/537.00 ms 重绘，不宣称所有组都稳定改善。
- 实时场景测得重复 `tag_configure` 和列宽写入为 0，它们不是当前每帧主热点；仍保留不重复设置、合并列宽计算的防护。

## 实际修改

- `gui_utils.py`：标准 Windows Cell 布局去掉冗余包装；不支持的主题保持原样。修复滚轮小 delta、双重类绑定处理，记录滚动时间。
- `performance_optimizer.py`：纯数据格式化/图标/标签后台准备，不持有 Tk 对象；GUI 短批次只写差量，少量单元格变化用 `set`。单活动任务＋单最新待绘帧；滚动结束跳过旧帧。链表式排序仅移动必要行，不逐行调用原生 `index`。
- `instock_MonitorTK.py`：启用 Cell 优化，滚动条也标记交互状态；排序不触发强制全表重写；列宽延迟合并、相同宽度不再写入；策略报告后台计算并只交付最新选择；修复短任务计时采样漏记。
- `JohnsonUtil/stock_sender.py`：在调用线程抓取开关快照，联动代理启动/恢复移到单工作线程，容量 1 队列保留最新意图；首次并发启动加锁。代理节流仍由原服务负责，不叠加本地 2 秒节流；本地降级保留原节流。
- `linkage_service.py`：进程标记只在子进程设置；代理创建加锁；队列满时停止流程不无限等待。
- `tests/test_tk_input_responsiveness.py`、`tools/benchmark_tk_interaction.py`：相关真实 Tk 回归及可复测隔离基准。
- `.gitignore`：仅放行本次测试和两份测量 JSON，避免证据被既有忽略规则遗漏。没有撤销用户已有修改或改动交易策略。

## 验证与剩余工作

- 本轮只运行 9 项新增相关回归：Cell 样式/字体保留、单元格差量、排序不调用 `index`、滚动后最新帧、列宽无重复写、列宽交互延后、非标准主题降级、并发单发送线程、代理/降级节流保持，均通过。因发送线程最后调整，另重跑 1 项直接相关的最新联动意图用例；未重跑已通过的整套 55 项。
- 增量测试首次有 3 处测试夹具问题（Tcl anchor 类型、模拟时间过期、模拟 ttk 缺少类型注解所需 Treeview），只修夹具并重跑失败项，未掩盖生产异常。
- 本轮之前已通过的排序/混合增删、选中项保留、自选图标标签、关闭期间无 Tk 写入、联动最新意图、策略报告最新选择、进程标记与满队列回归均保留；不以此替代实盘交易行为验证。
- 五个生产文件及工具/测试语法编译通过，工作区和暂存区差异检查通过。没有触发真实报警、联动或交易。
- **剩余已证实瓶颈：** 26 列同步重绘仍超过 200 ms；当前修复不能保证多列与 Qt 一样丝滑。只减刷新频率或增加 `after` 延时无法消除一次原生绘制的阻塞。
- 若继续做横向可见列窗口化，必须保留完整数据/排序，并同步解决总宽度、水平滚动位置、表头点击、列拖动和 `identify_column()` 映射；不能简单隐藏屏幕外列就上线。本轮没有贸然更换或重构表格框架。
- 全市场后台 DataFrame 复制/计算及 GIL 竞争、Qt 事件泵和其他主程序回调仍需完整运行时采样；隔离基准未证明它们不存在，也未据此改动报警和交易信号逻辑。
