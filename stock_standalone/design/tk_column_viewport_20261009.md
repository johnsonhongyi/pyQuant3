# Tk 主表横向可见列裁剪

## 本轮结论

- 已在现有 ttk.Treeview 上实现横向绘制裁剪，不是仅减少数据列，也没有替换整个表格框架。
- 完整数据列、每行 values、排序、选股字段和行情订阅保留；原生显示列表仅包含视口内列、两侧各一列缓冲及最多两个屏幕外宽度占位。
- 同一视口下，长组合的重绘成本已接近短组合。宽窗口真正可见的单元格仍多，不能承诺达到 Qt 或 60 FPS。
- 保留全部此前修改，本轮不再调整后台策略、报警、联动或交易代码。

## 实现

- 新增 `tk_gui_modules/column_viewport.py`，派生原生 `ttk.Treeview`；主表只改导入和实例化位置。
- 用完全在屏幕外的端点列承载隐藏列总宽度，保持总宽度及原生 xview/滚动条比例。没有向数据模型添加占位列，没有改动 values 顺序。
- Python 的 `displaycolumns`、列宽及配置查询仍返回完整逻辑配置；`identify_column`、`column/heading/set/bbox` 的 `#n` 参数映射回原逻辑列，防止横移后误触 code/name 或错误排序列。
- 表头原生拖动期间冻结物理列窗口，释放后同步实际宽度再裁剪；窗口缩放、水平滚轮、滚动条和列组合更换均更新视口。
- 几何更新使用单个合并 idle 任务；纯纵向滚动不会反复重设 `displaycolumns` 或计算列宽。
- 前轮的后台格式化、最新帧合并和滚动期间延迟行情 UI 写入保持不变；业务数据不因屏幕外列裁剪而停止接收或计算。

## 实测条件

- 从当前 `display_cols.json` 读取截图中的两套组合：默认规则 44 个配置列，加 code 为 **45 列**；连阳Upper-hmax 74 个配置列，加 code 为 **75 列**。配置文件未修改。
- Windows、Tk 8.6.12、vista、TkDefaultFont、Tk scaling 1.3333；视口高 600 px，宽分别为 1200/2938 px；code 80 px、name 240 px、其余 64 px，固定非拉伸列宽。
- 两组都使用上一轮已经优化的 Fast Cell 布局。因此“优化前”是上一轮优化后的 Treeview，不是最初未修复版本。
- 隔离已映射离屏窗口，合成中文/星号名称、数值和红色行标签，不启动交易程序或真实行情/联动；仅使用实际列配置，不等于实盘全流程负载。
- 每组 8 次，P95 为最近秩，当前样本量下等于最大值。纵向计时为调用后 `update_idletasks()` 的原生空闲重绘；横向为调用＋视口更新＋空闲重绘。
- 纵向每个样本验证真实位移。首次横向测试发现到达边界后有未移动样本，已作废并只重测横向部分；正式 JSON 的每个横向样本均验证真实位移。
- 不测物理输入到显示器呈现，也未重跑上一轮 26 列的事件延迟矩阵；两轮不同列宽/列数的绝对耗时不能直接相减。

## 剩余限制

- 屏幕内约 45 个显示项的同步原生绘制仍约 330 ms；本次消除的是屏幕外额外开销，并未把屏幕内真实数据省略掉。
- 全市场 DataFrame 准备、其他 Tk 回调、Qt 事件泵以及 Windows 实际呈现仍需运行中采样，隔离基准不能证明它们没有成本。
- 本轮未做全框架重写、原生 DLL 热补丁或截图覆盖式假滚动。需要重启主程序，才能加载新的 Treeview 派生类。
