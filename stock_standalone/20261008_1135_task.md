# 任务清单：修复 NextDayWatch TDX 实时轮询高频重复日志刷屏问题

**创建时间**：2026-10-08 11:35  
**对应需求**：修复 ATS NextDayWatch 实时轮询每 3~4 秒高频打印重复 `[NextDayWatch][ATS_TDX] ... candidates=192 quotes=192 quote_gaps=0 confirmed=39` 的日志刷屏问题。

---

## 1. 根因剖析与机制确权

1. **高频轮询机制**：
   - 在交易时段（09:30~15:05），`_poll_next_day_watch_tdx` 定时器以 4 秒（4000ms）为周期在后台执行 `_worker`。
2. **日志级别提升逻辑缺陷**：
   - 在 `ats/ui/main_window.py`（第 6237~6242 行）中：
     ```python
     confirmed_count = sum(1 for event in events_to_dispatch
                           if event.get("type") == "NEXT_DAY_WATCH_CONFIRM")
     log_summary = logger.info if confirmed_count else logger.debug
     log_summary("[NextDayWatch][ATS_TDX] service=TDXRealtimeFetcher node=%s endpoint=%s:%s candidates=%d quotes=%d quote_gaps=%d confirmed=%d elapsed=%.0fms", ...)
     ```
   - 原设计意图为“有确认事件时才输出 INFO，平时静默为 DEBUG”。
   - 但在真实盘中运行中，一旦候选池中有标的达成了确认（例如当前已确认 39 只，`confirmed_count = 39`），这 39 只标的在后续每次 4 秒轮询中都会处于已确认状态。
   - `confirmed_count > 0` 恒成立，导致 `log_summary` 永久为 `logger.info`。
   - 结果：每 4 秒向控制台输出一条完全一模一样的废话日志（1 分钟 15 条，1 小时 900 条），造成控制台严重刷屏。

---

## 2. 改造方案（KISS 原则：状态防抖 + 60s 心跳节流）

在 `ats/ui/main_window.py` 中引入轻量状态记忆与节流：
1. **状态特征元组**：`curr_state = (endpoint[0], endpoint[1], len(codes), quote_count, quote_gap_count, confirmed_count)`。
2. **提升为 `logger.info` 的必要条件（满足任一即打印 INFO）**：
   - 状态发生实质变更（`curr_state != _last_ndw_log_state`，如新增确认标的、节点切换、标的数变更）；
   - 存在行情异常缺口（`quote_gap_count > 0`，需即时告警）；
   - 缺口刚刚自愈归零（`prev_gaps > 0 and quote_gap_count == 0`）；
   - 距离上一次输出 INFO 已过去 60 秒（定期心跳汇总）。
3. **平稳无变化周期**：
   - 保持输出为 `logger.debug`（不干扰前台控制台）。
