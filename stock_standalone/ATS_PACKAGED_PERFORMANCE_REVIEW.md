# ATS 打包性能审查（2026-09-30）

## 结论：源码修复已实施，打包与实盘验收未闭环

修复前存在主线程同步网络、全市场扫描、无节流表格重绘以及 Qt 行情队列积压风险。单文件打包增加启动和退出成本，但不能单独解释运行期间持续高 CPU。

以下问题与行号保留为修复前审查记录；本轮已实施修复见文末。已安装 exe 尚未更新，不能将源码验证结果视为实盘卡顿已消除。

## 运行采样

- 已安装进程：PID 12516，D:\JohnsonProgram\instockMonitorTK\ATS_Terminal.exe。
- 3 秒线程 CPU 差分采样：12 个逻辑处理器，58 条线程，工作集约 1811 MB；最活跃的两条线程各约占单核 0.5%，其余显示 0%。采样时进程可响应，没有捕获高 CPU／卡死瞬间。
- 用户截图显示同一业务进程约占整机 CPU 17.6%、内存 1802.6 MB。整机百分比不能直接归因于主线程；高内存也不能直接证明泄漏。
- 小内存 exe 可能为打包引导进程；不能仅根据同名进程数量认定重复启动。

## 严重问题

### P1：新股面板仍在主线程同步加载数据

- `ats/ui/new_stock_panel.py:611`：生命周期初始化直接调用 `get_combined_new_stocks`，并非只读取持久化缓存。
- `ats/ui/new_stock_panel.py:808`：IPC 回调发现数据为空时再次同步调用相同函数。
- `ats/new_stock_fetcher.py:455`：TTL 未命中时继续获取 IPO 日历、解禁日历与行情，而不是立即返回已有磁盘数据。日历请求包含 3 秒、4 秒超时；这些超时不能当作整个调用的耗时上限。
- 影响：启动、切页或空缓存状态下整窗停止响应；后台已有加载任务也不能取消上述主线程调用。
- 修复方向：首帧只读现成缓存，所有补齐走现有 NewStockFetchWorker，并防止重复发起任务。

### P1：新股可见时每次行情都全表更新和排序

- `ats/ui/main_window.py:4859` 附近在启动 LedgerUpdateWorker 前同步调用新股面板更新。
- `ats/ui/new_stock_panel.py:838` 逐行、逐字段修改 DataFrame；`:964` 调用完整 `_render_table`，没有独立渲染频率限制。
- `ats/ui/new_stock_panel.py:1009` 起已有单元格仍反复设置文本、字体、颜色、背景、对齐与排序字段；`:1131` 使用逐行 apply 计算排序权重；`:1643` 恢复排序后再次 sortItems。
- 影响：IPC 的刷新频率可以高于“自动刷新(5s)”控件频率。关闭该控件并不代表停止 IPC 渲染；截图中的可见新股面板会持续消耗主线程时间。
- 修复方向：只合并最新行情，限制可见表格渲染频率，只修改变化的单元格，批量更新期间抑制绘制；排序按数据变化或用户操作触发。

### P1：IPC 接收没有针对 Qt 消费速度的队列上限

- `ats/ui/main_window.py:3824`：接收线程回调只负责 emit Qt 信号。
- `ats/ipc_bridge.py:373` 发出回调后，`:387` 回 ACK；这时界面可能尚未处理行情。
- socket 客户端队列有上限，但不等于 Qt 待处理行情信号有上限。当前链路没有把多个待处理行情合并成最新快照。
- 影响：渲染跟不上时可能积压大 DataFrame，增加内存与延迟；这是风险，尚未实测队列长度，不能直接断言 1.8 GB 全由此产生。
- 修复方向：行情使用“最新快照槽位＋至多一个待处理唤醒”；交易指令、成交和事件信号保持逐条处理。必须保留增量合并、版本和会话语义。

### P1：资金主线首帧／强制刷新可能同步等待 TDX 锁与网络

- `ats/ui/capital_dragon_panel.py:544` 附近无缓存且首次显示、或 force 时同步执行 `analyze_capital_dragon_universe`。
- `ats/capital_dragon_engine.py:605` 分析调用 `_fetch_tdx_index_data`；`:342` 等待共享 `_conn_lock`，随后可能连接、查询及逐个重试。
- `ats/tdx_realtime_fetcher.py:2436` 连接也持同一 RLock。锁是可重入锁，本次没有据此认定递归死锁，但等待其他后台任务会阻塞界面。
- 修复方向：首帧和强制刷新同样使用后台 worker；界面只读取已完成报告。

### P1：主线程“后台天梯”实际执行全市场逐行扫描

- `ats/ui/main_window.py:4925` 在结果槽中调用 `update_live_snapshot`。
- `ats/limit_up_engine.py:512` 直接调用扫描，`:555` 使用全市场 iterrows；不是注释声称的纯向量化后台计算。
- `ats/ui/daily_limit_up_dialog.py:1670` 的首帧也同步扫描。关闭 L2 网络仅去掉盘口请求，没有去掉 CPU 运算和名称回退。
- 修复方向：放入现有后台计算流程，多个面板共享扫描结果，主线程只读缓存。

### P1：心跳和冷启动同步等待命名管道

- `ats/ui/main_window.py:3649`、`:3678`、`:3838` 直接调用发送函数。
- `data_utils.py:1294` 起最多重试 5 次，管道忙时等待 1000ms，找不到时 sleep 0.5s；同步 WriteFile 也没有应用层超时。
- 影响：行情后端缺失或繁忙时界面可能停顿数秒；这类阻塞可以表现为低 CPU 的“未响应”。
- 修复方向：把同步请求放到有防重入的后台任务中，界面不执行管道等待或休眠。

## 重要问题

- P2：`ats/ui/new_stock_panel.py:2109` 单股测算在点击槽中同步执行 `evaluate_stock_tdx`。之前调用一次 processEvents 只能刷新提示，不能让后续测算变为异步。
- P2：`ats/ui/sbc_launcher.py:463` 起持仓关闭同步 wait，超时依次为 3、2、0.5 秒；`:648` 起批量关闭逐进程等待。按钮／菜单主线程调用期间会冻结，窗口数增加时成本叠加。
- P2：`ats/ui/main_window.py:4963` 的 Tier 3 及其中 singleShot 是主线程延迟调度，不是线程池。是否阻塞取决于具体弹窗回调，不能用“错峰”注释证明异步。
- P2：`ats.spec:123` 的 EXE 包含 binaries 和 datas、没有 COLLECT，属于单文件配置；每次启动独立 SBC 会重复承担打包启动成本。UPX 开启可能增加启动开销，实际部署是否由此 spec 构建尚未核对。
- P2：`run_ats.py:134` 在 QApplication 创建之前同步检查后端；`sys_utils.py:1251` 检测包含进程扫描及无超时 tasklist 兜底。影响首次出现窗口的时间，不足以解释整个交易时段高 CPU。

## 已检查的正常路径

- IPC 收包／解码有专用后台处理线程和有限客户端队列。
- LedgerUpdateWorker 有 busy 防重入及异常结果信号；并非每次行情无限创建 Ledger worker。
- 新股面板不可见时会保存最新 IPC 数据并跳过渲染。
- 大盘状态栏 `get_market_indices_and_volume_summary()` 无参数调用只读后台缓存；本次不把它误报为同步 TDX。
- 次日观察池行情轮询有后台线程与 busy 门禁。

## 本轮实施与验证

- IPC 合并保留会话边界，关闭时丢弃待消费帧；Ledger 忙时仅保留最新刷新请求，在线程完成后释放门禁。
