# ATS 卡顿与存储修复验收（2026-09-30）

## 原因与修复

- **后台线程没有隔离 GIL。** 卡顿进程采样中，次日观察线程占约 83% 的持有 GIL 样本，反复解析历史 JSON、序列化整份评估数据；检查点无限累计使历史评估文件达到约 100MB。现改为持久后台进程、内存缓存和每候选最多 64 个检查点，保留每日末点、首尾点、最大高点/VWAP 摘要、全部事件及投递回执。
- **热点榜定时槽仍同步扫描全市场并请求 TDX。** 捕获的 GUI 栈位于 `compute_hot_alpha_leaderboard → build_target_universe → get_security_quotes_safe`；网络等待和 GIL 争用均可表现为整机 CPU 未满却无法点击。现由防重入后台任务计算，GUI 仅渲染结果；冷启动也不在 GUI 初始化 TDX 单例。
- **策略存在性检查反复解析同一文件。** 新股刷新逐股读取策略 JSON，约 100 次重复解析/轮。现按文件版本复用代码索引，一轮只解析一次，兼容列表与字典格式。
- **MA20D 展示集合与交易准入集合混用。** 合法 MA20D 候选未进入交易池时，被第二阶段再次筛掉。现展示集合包含当轮有效候选，仍保持交易准入约束；回归确认空交易池也能显示观察候选。
- **对账每轮保存完整重复状态。** 历史文件累计数百 MB。现缓存最新完整快照，历史保存状态增量；真实订单/账户状态的业务持久化独立保留。
- 保留已有 IPC 最新快照合并、新股 500ms/主计算 1s 限频、异步扫描/管道/退出修复；MA20D 整批无变化直接跳过，变化批次只更新变化单元格。
- 股票名称的逐股补齐、行情批量名称注入、证券目录、行情/K 线缓存、天梯存档和信号会话存档均接入缓存；详情页 Trace 在后台加载并复用索引。
- IPO learning console 关闭时，不启动其 gate provider 自动刷新，也不写状态心跳；次日观察属于独立业务，按自身配置运行。
- 修复打包验收发现的表头保存 `sync` 参数不兼容，保存配置改为异步排队。
- 核对发现 PyInstaller 增量构建可能沿用旧 PYZ 模块，已清理过期缓存并用代码指纹逐模块核对；构建成功日志不作为源码已进入 exe 的证明。

## 存档约定

- 行情、评估、信号、对账等运行存档：首次必要加载后复用内存；每 30 分钟合并一次，gzip/既有压缩格式、临时文件原子替换。
- 仅交易日 09:30–11:30、13:00–15:00 允许周期写盘；非交易日、午休和开盘前不写这些存档。
- 交易日 15:00 后，有未保存变化时额外保存一次收盘数据；无变化不写，重复退出/重启和合作进程不重复保存同一存档。
- 待写数据在内存中合并。写入期间的新记录和新行情保留待写标记，投递回执只在真正持久化后确认；`force` 不能绕过时段及频率约束。
- 用户主动修改的配置、真实订单/账户及不可变业务事实保留既有持久化保障；本次没有把它们当作重复行情存档处理。未将启用后的整套 LLM 数据库改造成压缩文件。
