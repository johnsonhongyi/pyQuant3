# AGV 桥实施审核与 Web 选桥补齐

## 审核结论

源码已覆盖 AGV 桌面管理器、独立 CLI Worker、Go API 运行时/排队和 Web 选择入口，但整体尚未闭环。桌面 Worker 的全链路测试会直接合成成功回执，不启动 `agy`；真实 CLI、打包后的管理器和生产 Web→API→AGV→回执路径均未实测。

原方案文件仍标记“纯设计、不实施”，与当前工作区存在的 AGV 代码不一致，应视为历史方案状态，不能作为完成证据。

## 本轮源码调整

- Web AI 对话接入选择新增桌面 Antigravity；模型、推理强度、轮询、发送和全链路标记均按所选桥类型工作。
- 桥目录按 API provider 或 `agv-` 节点前缀区分引擎；设置页、聊天页和个股研究页只在同类型桥之间自动切换。无同类型桥时显示不可用，不再使用另一种引擎的模型/节点。
- Go API 拒绝桌面 provider 与节点前缀不匹配的运行时配置；桥测试根据显式节点类型路由。
- 增加 Web 路由/检测测试与 Go API 运行时/桥测试回归用例。

## 未闭环风险

- `desktop_antigravity_agent.py` 的 `bridge_test` 分支直接返回 `ANTIGRAVITY_BRIDGE_OK`，没有启动 CLI；测试界面显示的“模型回复/全链路通过”不能证明 Gemini 登录、模型调用或 stream-json 协议有效。
- 两个 AGV CLI 路径都使用阻塞式 `stdout.readline()`，同时把 `stderr` 接到无人读取的 PIPE；无输出/大量错误输出可能卡住 Worker。聊天空结果会补成“已完成分析”，策略输出不符合 Schema 时会补成 WATCH 结果，均可能把失败呈现为成功。
- Web 对话请求带有历史 `messages`，但 AGV Worker 只读取当前 `prompt`，未将历史上下文交给 CLI；多轮对话与 Codex 行为仍不等价。
- 没有 AGV Worker/管理器专项自动化测试；本轮未构建 PyInstaller 管理器，也未执行真实 `agy` 调用。
- 生产 Web 地址在当前工作区无法访问；本轮未部署，因此生产 UI/API 版本及线上桥名录状态未验证。

## 六次复核：`CLI_OUTPUT_CALLBACK_FAILED` 根因

- 根因：AGV 对话开始时先用 `chat-<job>` 作为临时 thread ID 回传进度；服务端 `chat_result` 要求 thread ID 为 UUID，因此拒绝进度回执并把 400 记入 `ProgressPublisher`。模型流开始后第一次 `publish()` 抛出该拒绝，`run_bounded_cli` 只保留了外层 `CLI_OUTPUT_CALLBACK_FAILED`。这也解释了界面为什么把 AGV 任务显示成“Codex Desktop 研究失败”：研究服务原先对失败前缀使用了 Codex 固定文案。
- 修复：进度在收到 AGY 的真实 `conversation_id` 前不带 thread ID；之后使用规范化 UUID；最终回执补齐冻结的 `reasoning_effort`。错误映射保留底层 HTTP 状态/peer code，研究错误前缀按 provider 显示。
- 回归：AGV 及桥运行时 Python 19 项通过，CLI 安全测试 12 项通过，Go `internal/httpapi` 与 `internal/stockanalysis` 测试通过。仅模拟输出流；没有进行真实模型调用。改动尚未部署，也尚未重启当前 AGV worker，实机确认仍待发布后的受控任务。
