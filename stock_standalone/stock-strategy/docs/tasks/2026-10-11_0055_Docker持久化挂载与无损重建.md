## 结论

stock-strategy 与 InStock 的业务数据已使用宿主机 bind mount；此前 InStock 根 crontab、`/etc/environment`、应用配置、源码变更和临时修复文件仍在容器可写层。已对这些状态做外置快照，并补齐 MariaDB 全库快照。没有停止或重建现网容器，没有部署新版本。

## 2026-10-11 发布架构决策修订

本审计中的“为 InStock 新部署唯一版本镜像、外置只读源码/配置/cron 并重建容器”是审计时提出的候选方案，不是当前批准的部署方式。后续总控决策明确：默认在现有 base/最新运行代码层中按审核 Git SHA 做一致性更新，不为普通功能更新增加 image/build；InStock 现有外置代码路径、挂载结构和 Docker 参数不得擅自改变。只有运行环境确需改变或用户明确要求隔离分层开发时，才按[全系统规范](../../../docs/engineering/全系统职责与Docker发布持久化回滚规范.md)走单次、唯一候选层及明确回滚验收。数据库、行情、缓存、日志等仍与代码/image 分离，恢复代码或 image 不得覆盖发布期间的新数据。

因此以下“从开发源码生成唯一 InStock 镜像与外置源码版本目录”的旧待办不再作为可直接执行的部署指令；应先按现行 InStock Docker 数据契约确认 Git 同步路径和实际容器挂载，不能据此改造现网结构。

## 代码约束

- InStock 新部署要求唯一版本镜像、外置只读源码、外置应用配置/环境/cron、四类现有业务 bind mount；容器根文件系统只读，临时目录用 tmpfs。
- stock-strategy 新安装与发布容器也使用只读根文件系统；初装脚本遇到已有容器会拒绝删除其可写层，现有服务必须经带备份与回撤的发布入口更换。
- 新入口会检查备份完成标记及校验和、数据库快照、当前数据挂载、配置与运行容器一致性、源码语法和候选镜像；失败自动恢复旧容器。回撤不会覆盖期间产生的数据库写入。
- 旧日期部署、源码热同步和迁移脚本已加拒绝执行保护，防止继续修改运行容器层或把备份写到容器 `/tmp`。
- stock-strategy 的部署与回撤入口会拒绝缺少/多余 bind mount，验证回撤快照 SHA256，并使用唯一临时目录原子恢复源码。
