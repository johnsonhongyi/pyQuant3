# ATS 多 Agent 主计划

## 最终目标

把 ATS 从“异动提示工具”升级为可审计的交易决策系统：市场事件感知 -> 结构信号 -> TradePlan -> 风险闸门 -> 模拟执行 -> 次日盈亏复盘 -> 参数迭代。

## 角色

- GPT/Codex（主脑）：总体架构、任务拆解、代码审查、测试闸门、验收、版本决策、风险决策和迭代规划；不得把自己直接实现并自测的业务功能标记为双 Agent 验收通过。
- Antigravity（Worker）：严格按任务书实施或独立审计、运行指定测试并提交可复核证据；不得自行扩大范围、批准版本、决定实盘上线或跳过 Codex 审查。
- 用户（最终负责人）：确认盘感是否被正确表达，批准高风险变更和实盘开关。

## 强制双 Agent 闭环

除紧急修复 Agent Hub、Orchestrator 或 Antigravity CLI 自身故障外，所有 ATS 业务功能必须执行以下流程，不得省略或以单 Agent 自测替代：

```text
GPT/Codex总体设计与任务拆解
-> Agent Hub任务书
-> Antigravity Worker实施或独立审计并提交证据
-> 编排器执行范围检查和测试闸门
-> GPT/Codex反向代码审查与验收
-> 修正或批准
-> 中文版本报告、Git提交和回溯节点
```

- Codex直接实现的业务代码只能标记为“待Antigravity独立复核”，在复核通过前不得标记为“双 Agent 验收完成”。
- Antigravity实现结果未经Codex审查、测试闸门和版本决策，不得归档、合并或进入下一交易阶段。
- 每个批准节点必须有任务编号、测试证据、审查结论、详细中文Git提交说明和版本报告记录。
- 事件情绪、潮汐状态机和实时总控接线等已由Codex直接实现的节点，必须通过已创建的独立审计任务补齐Antigravity第二视角复核。
- `.agent_hub/PROMPT_PROTOCOL.md` 是本闭环的工程级 prompt 协议，固定主控输出、Worker JSON 报告、发布门禁和冲突仲裁格式。

## 权限智能细分

- 权限同时按任务风险、工具类别和文件范围三维判定；任一维度越界都必须降级为人工确认或直接拒绝。
- P0_READONLY 用于审计复核，P1_DOCS_SAFE 用于文档和 Agent Hub 规则，P2_CODE_LOW 用于低风险实现，P3_CODE_MEDIUM 用于受控跨模块实现，P4_RELEASE_GATE 用于只读发布门禁，P5_FORBIDDEN 覆盖真实交易、密钥、自动发布和券商接口。
- `--dangerously-skip-permissions` 只允许在 P2/P3 且不高于 `max_auto_approve_risk` 的任务中由编排器注入；注入后仍必须执行 sandbox、范围检查、验证命令和 Codex 审查。

## Antigravity异常恢复规则

- 连接、Clash代理、Google服务可达性、OAuth认证、非交互权限、CLI参数、沙箱或本地配置异常，不构成跳过Antigravity的理由。
- 遇到上述异常时必须暂停当前业务实施，保留任务状态和原始日志，优先修复Antigravity CLI或编排器，运行认证探针和最小回声测试，恢复后从原任务继续执行。
- 不得因为短暂异常改由Codex长期替代Worker，不得伪造Worker交付物或把失败任务标记为完成。
- 只有Antigravity服务明确返回配额耗尽、速率限额或账户额度不可用，并保存可审计证据时，才允许将任务标记为“限额阻塞”。限额恢复后必须继续原闭环。
- 限额阻塞期间，Codex可以继续架构设计、任务拆解、只读审查和测试准备，但直接实现的业务变更仍须在发布前补做Antigravity独立复核。

## 硬约束

- `AUTO_MERGE=OFF`
- `AUTO_REAL_BUY=OFF`
- `AUTO_REAL_SELL=OFF`（结构止损自动化需单独批准）
- 任何 Agent 不得读取、输出或修改券商密钥。
- 同一业务文件同时只能属于一个 `running` 任务。
