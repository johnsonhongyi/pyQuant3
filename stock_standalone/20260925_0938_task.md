### 1. 瓶颈一：IPC 重复复制与规整、兼容合并分支及快照所有权
- **代码事实**：
  1. [`ats/ipc_bridge.py:128-189`](file:///d:/MacTools/WorkFile/WorkSpace/pyQuant3/stock_standalone/ats/ipc_bridge.py#L128-L189)：网络接收后台线程在收到 TCP 数据包后，首先执行 `df_norm = df_payload.copy()`，并在后台进行一次 MultiIndex 拆解与差分合并；合并完成后，执行 `df_to_deliver = self._cached_df.copy()` 将整个 5000+ 行宽表完整深拷贝一次；
  2. `IPCBridge._handle_client` 在约 225 行调用 `data_callback(df_to_deliver)`，经 `main_window.py:3746` 的信号到达 `_handle_realtime_data`；正常交付为裸 DataFrame，因此主线程通常走 `UPDATE_DF_ALL` 分支。入口重复复制和索引规整确实存在；主线程保留的 diff 合并属于兼容入口，不能据此认定正常链路每帧重复合并。
  3. [`ats/ui/main_window.py:80`](file:///d:/MacTools/WorkFile/WorkSpace/pyQuant3/stock_standalone/ats/ui/main_window.py#L80)：`LedgerUpdateWorker` 虽然采用了浅拷贝 `copy(deep=False)`，但在其 `run()` 中执行了 `target_df.to_dict('index')`，将大量行数据展开为 Python 字典。
- **性能危害**：
  多次复制、索引规整和字典展开会增加分配与 CPU 成本；10~30MB/s、30~80ms 均未实测。需区分 Python 对象分配、引用计数回收、循环 GC、NumPy 数据缓冲及 Qt 原生对象，不能将所有临时数组分配直接归因于 Minor GC。

### 2. 瓶颈二：通达信 (pytdx) 单一连接与全局锁争抢引发级联挂起
- **代码事实**：
  1. [`ats/tdx_realtime_fetcher.py:2028, 3280`](file:///d:/MacTools/WorkFile/WorkSpace/pyQuant3/stock_standalone/ats/tdx_realtime_fetcher.py#L2028)：`TDXRealtimeFetcher` 全局仅拥有一个 `TdxHq_API` 实例，所有 API 请求（`get_security_bars`、`get_security_quotes`、`get_index_bars`、`get_minute_time_data`）均受单一可重入互斥锁 `with self._conn_lock:` 保护。
  2. 尽管 SBC 图表窗口实现了 `SBCGlobalDispatcher` 进行集中轮询，但系统中的其他模块（例如新股次新雷达 `NewStockFetcher`、每日涨停天梯 `LimitUpEngine`、板块轮动挖掘机 `SectorRotationPullbackMiner`、分时策略引擎等）仍在各自独立的后台线程或定时器中直调 `TDXRealtimeFetcher`。
- **性能危害**：
  锁内网络请求可能拖延同连接的其他请求；后台数据停止刷新与 GUI 事件循环冻结需分别测量。只有确认主线程等待该锁、同步调用或被计算挤占后，才能归因为界面阻塞，不能从单锁结构直接推导全系统假死。

### 3. 瓶颈三：Qt 表格全量单元格操作与 DOM 重构风暴（缺乏视口虚拟化）
- **代码事实**：

  3. [`ats/ui/ipo_command_room_dialog.py:1599-1630`](file:///d:/MacTools/WorkFile/WorkSpace/pyQuant3/stock_standalone/ats/ui/ipo_command_room_dialog.py#L1599-L1630)：集中交易指挥室在每次 `refresh_data` 时，直接 `self.tbl_rank.setRowCount(len(ranked))` 并重新 `new` 出所有单元格 item，造成成千上万个 C++ Qt 对象频繁创建与析构。

### 4. 瓶颈四：计算密集型策略对 Python GIL 的挤占与主线程响应度下降
- **代码事实**：
  1. 虽然主窗口通过 `LedgerUpdateWorker(QThread)` 将重度计算剥离到后台线程，但在 CPython 运行时环境下，多线程仍然共享同一个全局解释器锁（GIL）。
  2. `LedgerUpdateWorker.run()` 中包含了大量耗费 CPU 的操作：
     - `_volume_profiler.update_market_context` 与成交量异动评分；
     - `CapitalDragonEngine` 资金主线龙头全市场分析；
     - `ChannelSwingCandidateEngine.evaluate_channel_swing_structure` 通道几何与斜率测算；
     - 循环构建历史价格与均线时序（`sum(sub20)/len(sub20)` 等纯 Python 算术循环）。
- **性能危害**：
  当后台 Worker 处于高负荷 CPU 循环时，主线程的 Qt 事件循环（用于处理鼠标移动、悬浮提示 ToolTip、窗口缩放、键盘切换）无法及时获取 GIL 执行权限，造成用户感觉界面“不跟手”、“有粘滞感”。

### 5. 瓶颈五：散弹式历史/价格补齐与主线程/线程池混乱调度
- **代码事实**：
  [`ats/ui/main_window.py:4412-4460`](file:///d:/MacTools/WorkFile/WorkSpace/pyQuant3/stock_standalone/ats/ui/main_window.py#L4412-L4460)：`_flush_batch_stock_prices` 每次防抖到期，直接启动原生线程 `threading.Thread(target=worker, daemon=True).start()`。
  在该线程内部，不仅动态导入 `from JSONData import sina_data` 并通过 HTTP 访问新浪，还尝试获取 `self.hdf5_history_lock`。若加锁超时（5.0秒），直接标记失败并进入冷却重试。
- **性能危害**：
  频繁创建和销毁 OS 原生线程增加内核上下文切换；在网络不畅或磁盘繁忙时，散弹式异步请求产生堆积，加剧资源竞争。

## 二、加载异步化体系深度重构方案（Async Architecture）

### 1. 核心目标与架构原则
- **主线程热路径降载（摄入回调 P95 <2ms，其他短回调 P95 <5ms，均为候选预算）**：
  主线程绝对禁止任何磁盘 I/O（SQLite/JSON/HDF5）、绝对禁止网络 I/O、绝对禁止 DataFrame 全表二次合并。主线程仅做接收渲染就绪数据并更新可见视口。
- **代际守卫与自适应跳帧丢弃（Epoch Guard & Drop-on-Busy）**：
  仅可替换可重建的展示快照和纯计算请求；差分需按基线顺序合并，账本状态转换与信号事件必须保序。采用一个运行任务加一个最新待处理槽，避免持续取消造成永远无结果，详见正式方案第六节。

### 2. 异步化重构具体设计

#### (1) IPC 数据接收与预处理的彻底异步化解耦
- **现状缺陷**：`IPCBridge` 按连接创建处理线程并共享缓存，主线程仍重复复制、索引规整和板块清洗；主线程另有兼容 diff 分支。
- **优化方案**：
  - Socket 接收与有序归并分开：受限接收任务只解析信封，唯一状态所有者负责 MultiIndex 解包、市场代码对齐、差分合并与纯内存映射，重计算不得阻塞收包；
  - 后台线程产出**只读、已排版、完全就绪的 `ImmutableMarketFrame`**；
  - 主线程接收版本化展示结果并更新引用；只有发布后的对象不再被写入、旧读者生命周期可控，才能减少防御性复制，不承诺仅凭指针赋值实现完整回调 <0.1ms。

#### (2) 策略引擎的“进程池 / 独立计算进程”解耦方案 (候选评估)
- **彻底解放 GIL 路线**：
  - 评估将 `LedgerUpdateWorker` 的计算负载（通道几何、支撑企稳、资金主线分析）移至独立子进程（利用 Python `multiprocessing` 或独立守护进程）；
  - **进程间传输机制**：
    - 先评估紧凑数值数组的小载荷传输；仅当序列化成为实测瓶颈时评估共享内存。填充、描述符传输、同步和结果回传仍有成本，不新增 Arrow 依赖作为默认前提；
    - 计算进程只处理纯函数，回传结果与输入版本；输出大小按实际行列测量，不预设 <10KB。
  - **收益边界**：独立进程隔离纯 Python 计算的 GIL 竞争，但仍争用 CPU、内存带宽和调度资源；只有总延迟收益覆盖进程启动与传输成本时才准入。

#### (3) 集中式长驻 Worker 线程与线程池治理
- **废除零散原生线程创建**：
  - 全局废除 `threading.Thread(target=...).start()` 的随意调用；
  - 引入统一的 `ATSThreadPool`（基于 `QThreadPool` 与任务优先级队列），严格控制最大并发并发数（如 `max_workers = 4`），避免线程爆炸；
  - 对于股票名称补齐、历史 K 线补全、离线数据库查询等慢速任务，统一提交给低优先级 Worker，避免挤占高频行情资源。

## 三、数据读取全流程优化方案（Data Ingestion Pipeline）

### 1. IPC 零拷贝借读契约（Zero-Copy Borrowing Contract）
针对系统内 DataFrame 多处 `.copy()`，先保留必要隔离复制，再确立可减少冗余复制的数据所有权与借读生命周期：

```
[IPC Socket] ──> (唯一写者 Single-Writer) ──> 产出 Versioned Sealed DataFrame
                                                       │
                                  ┌────────────────────┴────────────────────┐
                                  ▼                                         ▼
                     [借读者 1: 主线程 UI]                     [借读者 2: 策略 Worker 线程]
                     - 只读读取，严禁修改                      - 只读切片计算
                     - 持有发布后不再变更的快照               - 局部派生列显式副本隔离
```

- **规则 1（单一写者）**：仅允许 `IPCBridge` 或总线更新线程写入 DataFrame 底座；
- **规则 2（密封发布）**：版本号只是元数据，不能冻结 DataFrame；发布后生产者必须切换到新工作版本，旧版本在读者释放前不得原位更新或复用；
- **规则 3（安全借读）**：主线程与后台 Worker 仅持有只读引用，绝不在入口处执行全表深拷贝；
- **规则 4（写时复制隔离）**：若某一算法模块确需新增临时派生列，仅对该列或极小切片进行显式复制，严禁原位修改共享底座。

### 2. 全系统统一通达信调度中枢（ATSUnifiedDataDispatcher）
彻底解决多窗口争抢 `TDXRealtimeFetcher._conn_lock` 的根源痛点，将 SBC 的集中调度机制推广至全系统：

```
                              ┌──────────────────────────────────┐
                              │    ATSUnifiedDataDispatcher      │
                              │     (单一后台守护调度中枢)        │
                              └─────────────────┬────────────────┘
                                                │ 优先级队列排序
                                                ▼
       ┌────────────────────────────────────────────────────────────────────────────────┐
       │ P0 关键业务轨：持仓风险、必要状态核对；后台窗口隐藏不能降低关键业务优先级        │
       │ P1 活跃展示轨：可见图表与精选标的；报价沿用现有 40 只分批配置                   │
       │ P2 全局低频轨：板块指数、ETF、大盘全景 (15s~30s 错峰分段拉取)                  │
       └────────────────────────────────────────┬───────────────────────────────────────┘
                                                │ 有界队列、超时与批次间重新调度
                                                ▼
                                    ┌───────────────────────┐
                                    │  TDXRealtimeFetcher   │
                                    │ (单一网络长连接通道)   │
                                    └───────────────────────┘
```

- **全端收敛接入**：
  - 新股次新中心、涨停天梯、板块挖掘机、SBC 走势图等，**严禁绕过中枢直接调用底层 TDX API**；
  - 所有数据拉取需求统一提交注册至 `ATSUnifiedDataDispatcher`；
  - 调度中枢根据当前桌面窗口的**可见性与焦点状态**，动态提升当前激活标的的优先级，非激活标的自动降频或休眠；
  - 统一调度收敛直调与重复请求，但等待转移到调度队列；单个阻塞请求仍会造成队首阻塞，需配合截止时间、分批让出及受限故障隔离。

### 3. 多级分层持久化缓存（L1 内存 -> L2 RamDisk -> L3 本地磁盘）
- **L1 内存热缓存**：分时 240 根分钟 Bar、日 K 线最近 60 日数据，常驻 Python 内存字典（带 TTL 淘汰）；
- **L2 已有缓存层**：复用 `TDXGlobalCachePool` 的现有代际缓存与 RamDisk 路径；扩展前测命中率和重复驻留内存，不默认引入新格式或承诺 <1ms；
- **L3 本地磁盘冷存储**：历史归档按可恢复性批量异步写入；业务事件和必要账本数据保留原有持久化确认语义，不能统一推迟到收盘。

## 四、分段式优化架构方案（Segmented & Progressive Optimization）

“分段式优化”包含三大维度：**渲染分段**、**计算分段**、**传输分段**。

### 1. 渲染分段：Qt 视口虚拟化（Viewport Virtualization & Dynamic Windowing）
这是彻底消除 GUI 卡顿的杀手锏。

```
 真实全量数据列表 (100 ~ 500 行)
 ┌────────────────────────────────────────────────────────┐
 │ 行 000 ~ 019: 视口上方屏幕外 (无需创建/设置任何控件)    │
 ├────────────────────────────────────────────────────────┤
 │ 行 020 ~ 045: 👁️ 当前可视视口区域 (当前屏幕可见 25 行)  │ ──> 仅为这 25 行动态分配/更新单元格
 ├────────────────────────────────────────────────────────┤
 │ 行 046 ~ 200: 视口下方屏幕外 (无需创建/设置任何控件)    │
 └────────────────────────────────────────────────────────┘
```

- **核心实施方案**：
  - **先减少无变化更新，再评估 Model/View**：
    先复用现有 item、缓存样式并按脏单元格更新；仍超预算的表格再逐个迁移 `QAbstractTableModel` + `QTableView`。不默认在 QTableWidget 上自建复杂虚拟视口；
  - **仅更新可视行（Visible Rows Only）**：
    利用 `table.verticalScrollBar().value()` 以及 `table.rowAt(y)`，精准计算当前屏幕可视的首行 `first_visible_row` 与末行 `last_visible_row`；
    每帧只对 `[first_visible_row - 2, last_visible_row + 2]`（包含预加载缓冲行，约 30 行）执行单元格赋值与样式渲染；
  - **滚动事件按需补齐（Scroll-on-Demand）**：
    用户滚动时刷新新进入视口的行；耗时需覆盖取数、布局和绘制，不预先承诺从 80ms 降至 2ms；
  - **彻底废除 `setRowHidden`**：
    将策略过滤、重点关注筛选等逻辑前移至纯内存列表运算，生成**可视行索引映射表 `visible_row_map = [0, 3, 5, 8, ...]`**。表格的行数直接设置为 `len(visible_row_map)`，通过映射索引直接取数，彻底消除 Qt 内部的几何重排布局开销。

### 2. 计算分段：多层梯度错峰计算（Tiered Progressive Calculation）
将原来集中在一次 Worker 循环中的庞大计算逻辑拆解为三个梯度：

| 计算梯度 | 覆盖范围 | 触发频率 | 计算内容 | 耗时预算 |
| :--- | :--- | :--- | :--- | :--- |
| **Tier 1 (实时脉冲层)** | 全表标的 (5000只) | 逐帧响应 (1~2s) | 最新现价、涨跌幅、偏离度、成交量（纯向量化四则运算） | **< 3 ms** |
| **Tier 2 (核心防守层)** | 持仓与精选标的 (30~50只) | 错峰响应 (2~3s) | 支撑线位、破位失效预警、二次上车、止损离场点判定 | **< 15 ms** |
| **Tier 3 (全景深度层)** | 全市场候选与板块 | 低频扫描 (10~30s)| 资金主线龙头归因、全市场天梯排位、行业热力图、大级别通道拟合 | **< 80 ms** |

- **收益评估**：只对允许降低刷新频率的纯展示或统计工作分层；状态敏感策略保持原语义，CPU 降幅需同输入回放验证，不预先承诺 60%。

### 3. 传输分段：IPC 双轨分流传输（Fast Ticker Track vs Deep Analysis Track）
- **快轨 (Fast Ticker Track, 1s 周期)**：
  仅传输订阅范围或变更行的核心动态字段，规模按行数、类型和编码测量；5000 行 × 6 个 float64 数值已达 240000 字节，尚未计 code、索引与协议头，因此全市场快照不能直接承诺 <15KB；
- **慢轨 (Deep Analysis Track, 15s 周期或按需拉取)**：
  静态字段 `[name, category, concept]` 按版本更新，均线等按依赖失效更新；`vwap/rank` 可能盘中变化，实际轨道取决于策略时效要求，不能统一放入 15s 慢轨；
- 双轨为后期候选，先保留现协议；需要共同基线、字段时间戳和兼容能力协商，无法一致拼接时回退完整快照。

## 五、全流程性能优化实施方案规划（分阶段演进蓝图·纯规划）

为确保系统稳定性，避免“大拆大改”引入隐蔽 Bug，实施方案严格遵循“基线先行、热点分离、逐步推进、指标量化”的工程闭环原则：

```
  【阶段 0：性能基线采集与 Golden Samples 固化】 (必做：量化当前耗时，建立正确性门禁)
                     │
                     ▼
  【阶段 1：数据归并单写者、快照隔离与冗余复制削减】 (先保证协议与所有权，再减少复制)
                     │
                     ▼
  【阶段 2：全局数据调度中枢收敛与 TDX 锁争抢根治】 (全端收敛至统一调度，消除网络假死)
                     │
                     ▼
  【阶段 3：计算梯度分段与进程级/线程池解耦方案】 (多层错峰计算，保障主线程极速响应)
                     │
                     ▼
  【阶段 4：Qt 视口虚拟化与表格极致 In-Place 复用】 (仅渲染可视区域，根除 DOM 重绘风暴)
                     │
                     ▼
  【阶段 5：全流程长周期压测、内存防泄漏与容灾降级门禁】 (全天候稳定性与自动回退保护)
```

---

### 阶段 0：性能基线采集与 Golden Samples 固化（Telemetry & Profiling Baseline）

#### 1. 目标
对 ATS 运行过程中的各项耗时建立毫秒级精度的高频打点与遥测探针，量化各阶段耗时基准，并固化输入输出黄金样本。

#### 2. 核心测量指标（Key Telemetry Metrics）
1. **IPC 端到端吞吐时延**：从 TK 进程发送行情包，到 ATS 界面单元格完成重绘的总时长（P50 / P95 / P99）；
2. **主线程单次回调阻塞时间（Main Thread Event Loop Lag）**：统计 `_handle_realtime_data`、`_on_ledger_results`、表格更新等在主线程中的实际占用时长；
3. **TDX 网络锁等待耗时（TDX ConnLock Contention）**：统计各线程在 `with self._conn_lock` 处排队等待的真实时长与超时次数；
4. **内存分配速率与 GC 频率（Memory RSS & GC Pause）**：监测进程在 4 小时实盘运行中的 RSS 内存爬升曲线与 GC 暂停时间；
5. **Golden Samples 固化**：在盘中录制真实的 IPC 行情包、TDX 分时数据与账本输入，固化为自动化测试用例，确保后续任何性能重构不改变业务逻辑与数值计算结果。

---

### 阶段 1：数据归并单写者、快照隔离与冗余复制削减

#### 1. 目标
建立数据归并与快照所有权契约，减少正常路径的重复复制和规整，核对后再收敛兼容差分入口。

#### 2. 具体实施规划
1. **单一合并责任收敛**：
   - 改造 `ats/ipc_bridge.py` 的候选方案须先将多连接解析结果送入唯一归并者，再发布独立版本快照；
   - 核对全部调用者后减少主线程重复复制与规整；兼容 diff 入口经过调用审计和协议迁移后才能删除；
2. **只读引用借读契约落地**：
   - 主线程以只读引用持有底座；
   - `LedgerUpdateWorker` 严格遵循只读借读，取消内部多余的深度复制；
3. **指标验收门禁**：
   - 候选预算：行情摄入回调 P95 <2ms、P99 <5ms；所有权与协议保真测试先通过；
   - 记录每帧复制字节、分配率、驻留快照数及 GC 暂停，相对 Stage 0 对照评估，不预设 70% 降幅。

---

### 阶段 2：全局数据调度中枢收敛与 TDX 锁争抢根治（Unified Data Dispatcher）

#### 1. 目标
将 `SBCGlobalDispatcher` 升级为全系统通用的 `ATSUnifiedDataDispatcher`，终结多模块并发争抢 `_conn_lock` 导致的系统假死。

#### 2. 具体实施规划
1. **构建优先级请求队列（Priority Request Queue）**：
   - 将业务调用与底层网络解耦，上层模块仅发起数据订阅（如 `subscribe(code, type="1m", priority=P0)`）；
   - 调度中枢内部由单一守护线程按优先级驱动批量拉取，严格执行 40 只安全切块；
2. **窗口可见性智能感知与动态降频**：
   - 监听窗口的 `showEvent` / `hideEvent` / `changeEvent`；
   - 当某子窗口（如 SBC 走势图或涨停天梯）被最小化或隐藏时，自动将其订阅标的降级至低频轮询（从 3s 降至 30s）或暂停拉取；
3. **指标验收门禁**：
   - 同时统计锁等待与调度等待、请求超时、缓存年龄、关键业务截止时间违约率；不能只报告锁等待下降；
   - 注入慢请求后验证 GUI 响应、低优先级不饿死、队列有界及过期数据标识。

---

### 阶段 3：计算梯度分段与后台并发治理（Tiered Compute Pipeline）

#### 1. 目标
拆解策略计算大循环，实施三级错峰计算；治理线程生命周期，消除 CPU 密集型任务对主线程 GIL 的掠夺。

#### 2. 具体实施规划
1. **三级计算梯度落地**：
   - **Tier 1**（现价、涨跌幅、偏离度）：向量化快速计算，每秒直接刷新；
   - **Tier 2**（持仓与精选池通道策略）：每 2~3 秒错峰计算一次，结果通过局部增量更新；
   - **Tier 3**（全市场真龙主线与天梯排位）：每 15 秒低频刷新一次；
2. **长驻计算线程与代际守卫（Epoch Guard）**：
   - 废除频繁的 Worker 线程销毁与重建，维护常驻工作线程；
   - 纯计算在安全检查点判断取消；状态更新由唯一所有者保序提交，完成后消费最新待处理槽，不能半途丢弃已写账本的工作；
3. **指标验收门禁**：
   - 同输入、同策略语义下比较总 CPU 秒与尾延迟，50% 降幅仅作待验证期望；
   - Event Lag 候选 P95 <8ms、P99 <16ms，且明确采样口径；事件循环延迟不等于屏幕 FPS。

---

### 阶段 4：Qt 视口虚拟化与表格极致 In-Place 复用（GUI Virtualization）

#### 1. 目标
将 `SwingStateTable`、`FavoritePanel`、`IPOCommandRoomDialog` 等核心表格重构为视口虚拟化渲染架构，消除不可视单元格的无谓操作与 DOM 重建。

#### 2. 具体实施规划
1. **视口懒渲染引擎构建（Viewport Lazy Engine）**：
   - 仅对当前屏幕可见的行（约 25~35 行）进行 `QTableWidgetItem` 属性赋值与样式渲染；
   - 滚动时按需显示已准备好的数据，验证选中、排序、复制和导出一致性，不承诺 0 延迟；
2. **逻辑行索引映射表取代 `setRowHidden`**：
   - 纯内存中完成策略公式与自选股的布尔过滤，生成有效行索引列表 `[i1, i2, ...]`;
   - 表格直接展示过滤后的行数，消除全部 `setRowHidden` 几何重算；
3. **指标验收门禁**：
   - 候选预算：可见区域单次增量更新 P95 <3ms、P99 <8ms；另计排序、布局和真实绘制耗时；
   - 覆盖 50/300/1000 行、多个 DPI 与窗口尺寸，统计输入延迟和绘制间隔，不承诺任何规模 0 掉帧。

---

### 阶段 5：全流程长周期压测、内存防泄漏与容灾降级门禁（Resilience & Stress Testing）

#### 1. 目标
构建全天候无报单影子压测与自动化容灾降级体系，确保优化方案在极端行情与极端网络环境下的工程级稳健性。

#### 2. 具体实施规划
1. **影子实盘长周期压测（48~72小时连续运行）**：
   - 接入历史实盘全量 Tick/IPC 回放流，持续高频压测 3 个交易日；
   - 验证进程内存 RSS 上限、Handle 句柄数、GDI 对象数与线程数，严禁发生任何资源泄漏；
2. **自适应降级与异常自愈契约（Degrade & Self-Healing）**：
   - CPU >85% 或网络延迟 >3000ms 仅作为候选触发条件，还需队列年龄、持续窗口、恢复滞回与最小驻留时间；优先暂停预热和展示统计，关键业务频率不得统一延长到 15s；
   - 一旦资源恢复正常，系统自动无缝恢复全功能状态；
3. **指标验收门禁**：
   - 连续回放 72 小时无崩溃、无死锁，预热后内存与句柄无持续增长；有限测试只能表述为“未观察到泄漏”，不能证明零泄漏；
   - 所有自动化回归测试（包括账本一致性、信号判定保真度）100% 绿灯通过。

## 六、方案总结与实施边界（恪守纯规划·不修改既有工程代码）

本方案针对 ATS 系统全链路进行了全面细致的瓶颈剖析与方案设计：
1. **接口兼容性**：所有规划均在既有数据结构、既有 IPC 协议、既有数据库与现有 UI 架构内演进，不破坏任何外部调用契约；
2. **实施边界**：**本次任务严格定位于“方案深度剖析与实施方案制定”，不执行任何实际代码修改**；
3. **后续落地建议**：后续若启动实施，强烈建议按照 **Stage 0 -> Stage 1 -> Stage 2 -> Stage 3 -> Stage 4 -> Stage 5** 的准入驱动顺序，逐阶段开展性能实测与代码重构，每阶段均以 Golden Samples 作为业务保真与性能达标的双重验证门禁。
