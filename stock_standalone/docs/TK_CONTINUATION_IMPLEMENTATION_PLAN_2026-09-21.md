# TK 主链后续持续实施任务计划书

## 0. 文档属性

- 文档目的：明确 TK 主链后续的实施顺序、边界、产出和验收标准。
- 当前状态：阶段一、阶段二基线已完成；阶段三已启动第一项“信号收敛与直接买卖点输出”。后续阶段仍须按本计划验收后实施。
- 适用范围：Trading Kernel、ATS 交易指挥室、新股检测中心、PAPER 账户、策略扩展接口、状态对齐和未来券商适配器。
- 当前安全边界：继续使用 PAPER；不连接券商；不启用 LIVE_AUTO；不自动合并未经验证的策略。

## 1. 总体目标

将 TK 建设为一次打包、长期稳定运行的交易决策主链：

1. 所有信号先经过统一契约、策略筛选、风控闸门和状态机。
2. ATS、新股检测中心和交易指挥室只调用 `KernelGateway`，不访问 TK 内部实现。
3. PAPER 账户成为持仓、订单、现金、收益和状态对齐的唯一验证基准。
4. 策略、状态、审计和执行适配器可以独立替换，不需要修改已打包的 TK 主链。
5. 在收益和回放一致性没有达标前，任何真实券商能力只保留接口，不进入生产执行。

## 2. 当前基线与必须保持的事实

### 2.1 已具备能力

- `KernelGateway` 已提供版本化决策入口和账户读模型。
- API 主版本为 `1.0`，支持 `DecisionRequest/DecisionResponse`。
- 已预留策略、执行适配器、状态存储和审计流水四类扩展接口。
- ATS PAPER 执行已开始统一进入 TK 主链。
- PyInstaller 和 Nuitka 已增加 TK 模块收集保障。
- 对账审计以 `reconciliation_YYYYMMDD.jsonl` 按日落盘；30 天后压缩归档，默认保存压缩审计 365 天。
- 阶段三已加入指令收敛：同代码同方向去重，退出覆盖同轮开仓，轮动保持独立组合决议。

### 2.2 当前不能假设的能力

- PAPER 盈利不等于真实交易盈利。
- 当前信号数量多不等于信号质量高。
- 历史订单与当前持仓可能存在遗留差异，不能无审计地重写历史。
- `LIVE_AUTO` 接口存在不代表可以直接启用真实交易。
- 旧测试中的自动 BUY 预期不一定符合当前策略规则，需单独更新夹具和预期。

## 3. 实施原则

### 3.1 单一事实源

- 当前持仓以 PAPER 执行账户快照为准。
- 当前策略状态以 TK `StateStore` 为准。
- 订单流水以 TK 审计记录为准。
- 收益统计从订单流水和持仓快照派生，不在 ATS 内重复维护第二本账。

### 3.2 先验证、后扩权

每一阶段必须先完成回放和 PAPER 验收，再允许进入下一阶段。任何阶段出现账户不一致、重复订单、状态回退或风控绕过，立即停止扩权并回到上一稳定版本。

### 3.3 契约优先

外部模块只依赖 `contracts.py` 和 `KernelGateway`。不得新增对 `TradingKernelService`、内部适配器字段或内部状态机实现的直接引用。

### 3.4 可回滚

每个阶段都要保留：代码提交号、配置快照、测试结果、PAPER 账户快照、审计流水位置和回滚步骤。

## 4. 分阶段任务

## 阶段一：TK 主链基线冻结

### 目标

冻结 API `1.0` 的字段含义、动作集合、拒绝码、状态集合和模式切换规则。

### 任务

1. 建立 API 字段表：字段类型、必填性、默认值、单位、允许范围。
2. 固定动作语义：`BUY`、`ADD`、`REDUCE`、`SELL`、`HOLD`、`BLOCK`。
3. 固定状态迁移：`FLAT`、`ARMED`、`IN_TRADE`、`EXITING`、`COOLDOWN`。
4. 固定模式权限：`OBSERVE` 只观察，`PAPER` 模拟执行，`CONFIRM` 人工确认，`LIVE_AUTO` 暂不开放。
5. 建立 API 兼容测试，确保主版本不一致时请求在进入内核前拒绝。
6. 给每次打包生成构建指纹，记录 API 版本、Kernel 版本和 Git 提交号。

### 产出物

- API 字段和状态迁移表。
- 版本兼容测试报告。
- TK 构建指纹文件。
- 主链冻结检查清单。

### 验收标准

- 外部模块不需要导入 TK 内部服务即可完成提交和查询。
- 同一请求在回放环境中得到稳定的 Trace ID、动作和拒绝原因。
- 旧主版本请求不会改变持仓、状态或审计流水。

## 阶段二：数据自动对齐与账户一致性

### 目标

让行情、信号、订单、持仓、状态和收益统计使用同一套时间、代码和数量标准。

### 任务

1. 统一证券代码格式、市场后缀、名称和交易日字段。
2. 为每条信号增加 `request_id`、`trace_id`、信号时间、数据时间和来源。
3. 统一价格、数量、金额、仓位比例的精度和单位。
4. 建立行情快照新鲜度校验，过期或跨日数据不得直接执行买入。
5. 每次启动时执行持仓与状态对账，记录新增、消失和状态变化代码。
6. 订单流水采用追加写入；发现历史差异时只生成对账报告，不直接篡改历史。
7. 建立现金、持仓、订单和状态的周期性快照。

### 产出物

- 数据标准化映射表。
- 启动对账报告和周期对账报告。
- 账户一致性监控面板。
- 差异分类：可自动修复、需人工确认、禁止修复。

### 验收标准

- 同一代码在 ATS、TK、PAPER 账户和收益统计中完全一致。
- 重启程序后持仓和状态不回退。
- 重复信号不会产生重复订单。
- 对账异常可定位到代码、时间、流水和 Trace ID。

## 阶段三：信号降噪与直接买卖点输出

### 目标

把杂乱信号收敛成少量可执行候选，不让低质量提示淹没交易指挥室。

### 任务

1. 设置信号分层：观察、候选、可执行、退出、禁止。
2. 对同一代码同一方向进行时间窗口去重和合并。
3. 强制显示买入理由、触发条件、止损价、目标价、仓位比例和失效时间。
4. 对信号执行前重新获取快照，避免使用过期价格和过期指标。
5. 将拒绝原因结构化显示，不再只显示“未执行”。
6. 在交易指挥室只突出最高优先级候选，其他信号进入可折叠历史区。
7. 对 `BUY`、`ADD`、`REDUCE`、`SELL` 分别建立统计，不混合计算命中率。

当前实施进度（2026-09-21）：阶段三已完成。
- 任务 1 已完成：`IPOOrderDirective.signal_state` 统一为 OBSERVE / CANDIDATE / ACTIONABLE / EXIT / BLOCKED。
- 任务 2 已完成：同代码同方向先做收敛，再执行 120 秒时间窗去重；仓位、止损、失效时间变化会形成新指令，不会被误吞。
- 任务 3 已完成：直接买卖点显式展示触发价、仓位、止损/结构失效价、目标 1/2、失效时间和决议依据。
- 任务 4 已完成：进入 TK PAPER/LIVE 适配器前重新读取最新个股快照，校验指令年龄、快照新鲜度、价格漂移和结构失效；不合格指令不得进入执行内核。
- 任务 5 已完成：拒绝原因结构化为 `reject_code / reject_reason / execution_status`，并写入历史流水。
- 任务 6 已完成：交易指挥室只消费 `get_pending_directives()` 的最高优先级收敛视图；被过滤信号记录到历史流水。
- 任务 7 已完成：BUY / ADD / REDUCE / SELL 分别统计执行、拒绝和过滤次数，并提供 `get_buy_sell_quality_daily_report()` 日报接口。
- PAPER 与未来 LIVE 共用同一执行前门禁；当前未自动开启 LIVE。
- 明日实盘准备新增只读 `KernelGateway.get_live_readiness()`，可在不切模式、不自愈持仓、不下单的前提下检查柜台、KillSwitch、账户快照、持仓一致性和内核版本。
- LIVE 安全硬门禁已补强：默认 `BrokerExecutionAdapter` 基类仅允许接口/内存仿真，禁止升格 `LIVE_AUTO`，必须注册真实物理券商适配器后才能通过；当前仓库尚未发现 QMT/MiniQMT/XTQuant 实盘适配器，因此真钱实盘仍处于 BLOCKED 状态。

### 产出物

- 统一信号状态模型。
- 交易指挥室候选列表和执行详情。
- 信号去重、合并和失效规则。
- 买卖点质量日报。

### 验收标准

- 操作员能从一条候选直接看到“是否可执行、为什么、执行多少、风险在哪里”。
- 相同信号不会在短时间内反复刷屏或重复提交。
- 每条执行或拒绝都可追溯到策略、数据快照和风控结果。

## 阶段四：策略插件化与收益验证

### 目标

让策略可以独立迭代，但必须通过同一 TK 风控和状态链，避免策略各自下单。

### 任务

1. 以 `StrategyProvider` 接入一套最小策略作为参考实现。
2. 统一策略输出为 `DecisionIntent`，禁止策略直接调用执行适配器。
3. 为每个策略记录版本号、参数集、特征版本和数据范围。
4. 建立按策略、市场、信号类型和持仓阶段拆分的回测统计。
5. 加入交易成本、滑点、涨跌停、最小交易单位和现金约束。
6. 建立训练/回测/仿真数据隔离，禁止未来数据泄露。
7. 只有满足收益、回撤、胜率、盈亏比和样本量门槛的策略，才进入 PAPER 观察池。

### 产出物

- 策略插件模板。
- 策略版本注册表。
- 回测报告和 PAPER 对照报告。
- 策略淘汰及降级规则。

### 建议验收门槛

- 样本量达到预先约定数量。
- 扣除手续费和滑点后仍有正期望。
- 最大回撤、连续亏损和单标的暴露未超过风控上限。
- 回测与 PAPER 的信号分布、成交率和拒绝率可解释。

## 阶段五：CONFIRM 人工协同验证

### 目标

在不接券商的前提下，验证“指挥室直接决策—人工确认—PAPER 执行—审计回放”的完整链路。

### 任务

1. 所有确认弹窗显示完整决策摘要和风险结果。
2. 确认、拒绝、超时和修改仓位都写入审计流水。
3. 人工确认不能修改代码、方向和风控结论，只能在允许范围内调整数量。
4. 验证多窗口、重复点击和程序重启情况下的幂等性。
5. 对人工确认后的成交结果与原始信号进行差异统计。

### 验收标准

- 每次确认只有一个最终订单结果。
- 重复点击不产生重复成交。
- 弹窗关闭、超时或异常时默认拒绝，不默认成交。
- 审计记录足以还原人工看到的内容和最终执行结果。

## 阶段六：券商适配器预留与隔离验收

### 目标

只设计和验证券商接口，不在本阶段启用真实交易。

### 任务

1. 定义券商适配器的连接、下单、撤单、查询持仓、查询资金和回报回调接口。
2. 定义券商错误码到 TK 拒绝码的映射。
3. 建立模拟券商适配器，模拟网络超时、部分成交、撤单失败、重复回报和断线重连。
4. 验证幂等键、订单状态机和回报顺序错乱处理。
5. 验证 Kill Switch、日亏损限制、最大暴露和人工确认门槛。
6. 设计凭证隔离、日志脱敏和最小权限配置。

### 绝对禁止

- 在没有完成 PAPER/CONFIRM 验收前填写真实账户凭证。
- 以测试模式名义发送真实订单。
- 让券商适配器绕过 Gateway 直接修改 TK 状态。
- 用真实账户回报覆盖 PAPER 历史流水。

### 进入真实交易的前置条件

- 所有关键回放测试通过。
- PAPER 与 CONFIRM 连续运行达到预设观察周期。
- 对账差异为零或全部有人工结论。
- Kill Switch 和断线恢复经过演练。
- 有明确的人工值守、限额、回滚和停机方案。

## 5. 测试与发布门禁

每次发布必须按以下顺序执行：

1. 静态检查和编译检查。
2. 契约、边界、状态并发和幂等测试。
3. 回放等价性测试。
4. PAPER 账户和对账测试。
5. CONFIRM 人工流程测试。
6. Nuitka/PyInstaller 打包前置检查。
7. 在隔离目录启动打包产物，执行只读能力握手和 PAPER 冒烟测试。
8. 生成发布报告，记录 Git 提交号、API 版本、内核版本和测试结果。

任何一个门禁失败，都不得进入下一环境；不得通过修改测试、关闭风控或手工改流水来“修复”发布结果。

## 6. 运营指标

交易指挥室需要持续显示以下指标：

- 候选信号数、去重后信号数、可执行信号数。
- BUY、ADD、REDUCE、SELL 的执行率和拒绝率。
- 各拒绝原因数量和趋势。
- 数据过期、跨日、缺字段和对账异常数量。
- 重复请求拦截数量。
- PAPER 现金、持仓、组合暴露、日盈亏和最大回撤。
- 策略版本收益、回撤、胜率、盈亏比和连续亏损。
- Gateway 错误、适配器超时和审计写入失败。

## 7. 风险与停止条件

出现以下任一情况，立即停止新策略接入和执行权限扩展：

- 账户快照与状态机出现无法解释的差异。
- 同一请求产生多个订单。
- 订单流水无法通过 Trace ID 还原。
- 过期行情仍能触发新的买入。
- 风控拒绝后仍有执行结果。
- 回测和 PAPER 结果差异无法解释。
- 打包产物缺少 Gateway、契约或执行适配器模块。
- 任何真实交易风险开关状态不明确。

## 8. 最终交付形态

最终应形成以下可交付集合：

- 一个固定版本的 TK 主程序。
- 一份稳定 API 契约和扩展说明。
- 一套 ATS 交易指挥室和新股检测中心统一入口。
- 一套 PAPER 账户、订单、持仓、状态和收益对账报告。
- 一套策略版本和收益验证报告。
- 一套可替换但默认禁用的券商适配器接口。
- 每个版本对应的构建指纹、测试证据和回滚说明。

本计划完成后，系统才具备从“信号展示工具”逐步收敛为“可审计的交易指挥室”的条件；在此之前，所有新增能力都必须停留在 PAPER 或人工确认范围内。
