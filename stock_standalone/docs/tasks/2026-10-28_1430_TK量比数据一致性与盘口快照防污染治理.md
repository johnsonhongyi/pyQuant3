# TK 监控主界面「量比」数据一致性与盘口快照防污染闭环治理

## 1. 任务背景与用户问题现象
- **用户反馈**：
  - "tk的量比出现严重的bug,全面检查数据一致性"
  - "刷新后又正常了,修复这是哪里的逻辑bug导致的"
- **现象对比剖析**：
  - **图1（13:38 异常态）**：
    `Stock Monitor` (TK) 界面中，表头为「量比」的列显示了原始累计成交量数值（如 `301005 超捷股份`: `113764`, `688536 思瑞浦`: `598257`, `688835`: `158965`, `000559`: `104171` 等几万~几十万的整数，状态栏显示 `Rows: 134`）。
  - **图2（13:43 正常态）**：
    用户按刷新后，表头同为「量比」的列恢复为标准的量比浮点数（如 `1.3`, `1.6`, `2.2` 等，状态栏恢复为 `Rows: 55`）。

---

## 2. 根因深度剖析（Root Cause Analysis）

1. **直接污染源（`_refresh_ui_favorites` 盘口快照覆写主表量比）**：
   - 在 `instock_MonitorTK.py` 中，`_refresh_ui_favorites` 每隔 2~10 秒后台拉取重点关注/联动行情快照（`linkage_quotes`）。
   - 盘口快照（来自通达信原生 API 或网络快照）包含原生字段 `volume`，其真实含义是**当日累计成交量（手）**（例如 301005 当时累计成交 `113764` 手）。
   - 而在主界面监控表格中，列名 `'volume'` 映射的显示表头是 **「量比」**（通常是 0.5~3.0 的浮点数），真正的成交量存放在 `'vol'` 列中。
   - `_refresh_ui_favorites` 在执行字段合并时：
     - **主表已有行（`matches` 分支）**：
       无条件遍历盘口字段：`df.at[row_index, column] = value`，直接将 `quote_values['volume']`（113764 手）粗暴覆写了主表格中的 `df.at[row_index, 'volume']`（原本正确的量比 1.3）！
     - **重点关注未在当前筛选中的行（`else` 分支）**：
       即使从 `rich_row`（全市场已计算指标的快照）提取了正确的量比，随后执行 `merged.update(quote_values)`，再次被盘口的 `volume`（成交量）覆盖，并将这批行作为 `added_rows` 强行追加到了当前主表中，导致当前主表行数从 55 行暴增到 134 行！
     - 最终调用 `self.refresh_tree(frame, ...)`，导致主界面的「量比」列瞬间被数十万的原始成交量撑爆，行数变成 134。

2. **为什么“刷新后又正常了”**：
   - 当用户点击刷新，或者后台主数据管道（`_run_compute_async` -> `_apply_tree_data_sync`）完成下一轮行情计算交付时：
   - 主数据管道交付的是 `complete_indicators_pipeline` 过滤后的纯净 55 行数据，此时 `df['volume']` 是由 `calc_compute_volume` 计算出的真实量比（如 1.3），行数恢复为 55 行。
   - 然而，一旦 `_refresh_ui_favorites` 再次执行（10秒内），由于上述覆盖逻辑的存在，又会把 113764 等成交量写回界面，并再次膨胀为 134 行！

3. **数据管道与 UI 消费端的潜在隐患与防御缺失**：
   - **`stock_selector.py` 内部曾存在反向赋值**：`combined_df['volume'] = combined_df['vol']`，混淆了成交量与量比的语义。
   - **`data_utils.py` 缺少全局双向镜像**：计算完成量比后未同步写 `vol_ratio`，使得下游在面对字段混淆时缺乏 SSOT 权威量比列作为自愈参考。
   - **UI 消费端（Treeview 增量更新与传统更新）零防御**：`TreeviewIncrementalUpdater._prepare_rows_fast` 在提取 `'volume'` 列时完全无条件信任输入值，直接把大于 100 的数值输出到了表头为「量比」的列中。

---

## 3. 治理与修复方案

### 阶段一：阻断根源污染（源头止血）
1. **彻底修复 `instock_MonitorTK.py` 中的 `_refresh_ui_favorites`**：
   - 在将 `quote_values` 更新到主表已有行（`matches` 分支）时：
     - 若 `column == 'volume'`，坚决不覆写主表的 `'volume'` 列！将盘口原始成交量安全存入 `df.at[row_index, 'vol']`；
     - 严格保留主表已有的正确量比！
   - 在将重点关注标的作为 `added_rows` 追加时（`else` 分支）：
     - 剔除 `quote_values` 中的 `'volume'` 后再与 `rich_row` 合并，确保 `rich_row` 中已计算好的量比不被盘口原始成交量冲刷；盘口成交量安全存入 `vol`；
     - 没有 `rich_row` 时，将盘口成交量放入 `vol`，`volume` 兜底为 `1.0`，绝对禁止将几万几十万的成交量塞给 `volume`。

2. **彻底规范 `stock_selector.py` 中的 `combine_live_data`**：
   - 移除 `combined_df['volume'] = combined_df['vol']` 危险反向覆盖；
   - 明确量比存入 `vol_ratio` 与 `volume`，成交量严格归属 `vol`，彻底杜绝数据源歧义污染。

### 阶段二：管道端 SSOT 双向权威对齐
3. **在 `data_utils.py` 的 `calc_indicators` 中双向对齐 `volume` 与 `vol_ratio`**：
   - 计算完成量比后：`top_all['vol_ratio'] = top_all['volume']`，建立全系统不可篡改的双重权威索引。

### 阶段三：UI 消费端终极自愈防线
4. **在 `performance_optimizer.py` 的 `TreeviewIncrementalUpdater._prepare_rows_fast` 建立量比数值防御与智能自愈**：
   - 当 `col == 'volume'` 时：
     - 若数值异常偏大（`> 100`，明显是 113764 这类成交量脏数据）：
       1. 优先从同行的 `vol_ratio` 提取真实量比；
       2. 若无 `vol_ratio` 但有 `last6vol`，通过 `vol / last6vol` 现场自愈纠偏；
       3. 若均无法计算，安全回退兜底为 `1.0`，**坚决禁止在「量比」列向用户渲染出几十万的绝对成交量**！
     - 统一浮点数格式化为保留 1 位小数（如 `1.3`、`0.9`）。
5. **在 `instock_MonitorTK.py` 的 `_refresh_tree_traditional` 与 `show_first_frame` 中同步增加相同的量比防污染自愈逻辑**。
