## 重要问题

### R1 / P1：仅导入请求切换同源，其他联动接口仍使用原 Go 地址

- 位置：`stock-strategy/source/easy-stock-web/src/lib/linkage.ts:248`、`:220`、`:268`、`:278`、`:295`；公共请求函数 `src/lib/backend.ts:1958`。
- 条件：页面来自 `http://内网IP:20073`，配置仍保存同主机 `http://内网IP:20081`，Go 没有管理令牌。这正是交接描述的场景。
- `importLinkageSetup` 只为本次导入构造同源 config，没有更新调用方配置；targets/context/events/attention/commands 继续直连 `config.backendUrl`。
- Go `authorizedLinkageAdmin -> linkageLANRequest` 校验完整 Origin/Host，包括端口，后续请求仍会被拒绝；存在“配置成功，读取或关注操作仍 401”的路径。
- 建议：统一浏览器联动接口的网关解析，保留供 TK 回调使用的真实 `backend_base_url`。不要把 HMAC 密钥当管理令牌。
- 现有新增测试只覆盖导入 URL，缺少同一配置下随后读取与关注操作的连续调用覆盖。

### R2 / P1：TK 首次 synced 后不再更新该操作的行情状态

- 位置：`instock_MonitorTK.py:7844`～`:7859`；`:7911` 的心跳修改；`system_linkage_gateway.py:943` 的心跳接收逻辑。
- 首次回执持久化成功就从 `_tk_linkage_pending_receipts` 删除操作；心跳改动同时删除了原来逐操作的 `report_consumer_batch` 更新。
- 网关心跳仅更新总体 health，并将 not_running 转 pending；不会更新已 synced 操作的 quote_status。
- 因此首次 synced 携带 pending_fetch/stale/quota_limited 后，即使行情恢复 ready，该操作仍可能停留旧状态；反向 ready→stale 也失去逐操作更新。
- 与新 Web `isLinkageOperationSettled` 联用时，synced+pending_fetch 不能收敛，会持续轮询，影响用户判断和后台请求负载。
- 建议：把“已消费关注版本”与“行情状态持续更新”分开维护；使用已消费游标更新仍有效操作，不重新证明未消费版本。
- 当前 Tk 新测试只断言首次 ACK 与旧版本拒绝，没有覆盖同一版本下 pending_fetch→ready→stale。

### R3 / P1：异步关注写入完成后，Qt 公共分发器同步执行全局刷新

- 位置：`ats/ui/favorite_actions.py:54`～`:56`；`ats/ui/main_window.py:8112`～`:8275`。
- 分发器回到 GUI 线程后，直接调用 `_safe_favorites_changed()`；该方法逐只关注股匹配行情、格式化，更新多张表、策略池、热力图及打开的弹窗。
- 关注存储监听器也通过 `_handle_linkage_store_changed` 调用同一刷新；部分调用方还有本面板 completion 回调。同一次变更可能重复进入多条重刷路径。
- 写盘被移出 UI 是有效改进，但完成回调没有合并或时间预算，多概念窗口及大关注列表时仍会挤占 GUI 线程。
- 建议：按关注版本合并重复通知，后台准备数据，UI 仅分片应用差异；消费回执在对应版本实际应用后确认。
- 这是静态调用链证据，不将此前线上 4.98 秒的 TK 回调耗时套用于这份尚未确认打包的 Qt 工作区代码。

## 次要但需修复的问题

### R4 / P2：Qt 默认成功消息为 None，显示时异常被静默吞掉

- 位置：`ats/ui/favorite_actions.py:57`、`:61`、`:117` 附近。
- 提交函数默认 `success_message=None`，仍把该键放入事件；`event.get(key, default)` 返回 None，随后 `message[:180]` 抛 TypeError，被裸 except 吞掉。
- 多个调用没有传 success_message，写入成功但状态栏没有确认反馈；不会因此回滚已保存状态。
- 建议：使用 `event.get('success_message') or '重点关注已保存'`，并记录分发器内部异常。

### R5 / P2：Web 多节点证据读取与 Go 新的数据结构不一致

- 位置：`stock-strategy/source/easy-stock-web/src/components/WatchlistLinkageButton.tsx:280`、`:289`、`:293`；`src/lib/linkage.ts:110`。
- Go 改为按 node_id+source_id 保留多份证据；Web 类型仍没有 node_id，显示时只 find(source_id)，取同一来源的第一份。
- 同一 workspace 有多个节点时，切换 selectedNode 不会改变所选证据，可能把另一节点的角色或竞价候选显示成当前目标的证据。
- 建议：补充 node_id 类型，明确按目标节点筛选，或明确显示并区分各节点；单节点场景不受影响。

### R6 / P2：目录验证在 attention 幂等重放之前执行

- 位置：`stock-strategy/source/easy-stock-analysis/backend/internal/httpapi/linkage_attention.go:63`～`:73`、`:131`；`internal/linkage/attention.go:95`。
- HTTP 层先验证新增代码仍在当前目录，随后才进入服务层检查 intent_id 是否已应用。
- 已成功写入、但客户端未收到响应的 add，在目录暂不可用、过期或该证券后来移出目录时重试，会提前失败，拿不到既有成功回执。
- 建议：先验证并返回匹配请求内容的持久幂等结果，仅对新意图执行最新目录校验；不得因此放开新股票验证。

### R7 / P2：TK 写入完成回调队列满后直接丢失结果

- 位置：`instock_MonitorTK.py:11991`～`:12003`；`global_favorites.py:41`。

- 建议：为完成结果保留可重试、有界的交付机制；刷新脏标记可合并，用户操作确认不能静默丢弃。
