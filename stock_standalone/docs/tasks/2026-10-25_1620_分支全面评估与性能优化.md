# 分支全面评估 · 回测 · 性能压测（2026-10-25）

分支 `feature/signal-fusion-ladder`（相对 `main` 27 个提交、43 个源文件、+10293 行）。
本文回答四件事：设计实现有没有问题、回测跑到什么程度、性能到不到极限、闭环断在哪。

---

## 一、架构评估

### 1. 分层与职责分离（符合 AGENTS.md 要求）

| 层 | 文件 | 职责 | 评估 |
|---|---|---|---|
| 信号产生 | `engine.py` `anomaly.py` `strength.py` | 四轴评分 + 风险否决 → L0~L4 | 与决策层解耦，阈值可配置 |
| 归因 | `vanguard.py` `lifecycle.py` | 板块内领先度、战役阶段 | 只回答"这是谁"，不回答"买不买" |
| 连续判断 | `tracker.py` | 发令枪/证据链/第一波入局/入局后才剔除 | 唯一状态机，跨日落盘 |
| 收敛 | `ranking.py` `deploy_path` | 四道闸门 → 打分排序 → 可下单清单 | 本轮改造重点 |
| 持仓决策 | `trap.position_decision` | T+1 清仓/减半/持有 | 与入局分离 |
| 复盘 | `panel.py` `review.py` `trade_sim.py` | 统计、建议阈值、T+1 模拟 | 只读 |

### 2. 数据不变量（守住）

- 缺失数据给**中性**而不是 0：`engine.py` 的 `s_minutes`/`s_vel`/`s_sector` 在字段缺失时显式中性化，不用"零拉升"冒充。
- 无未来函数：历史回放 VWAP10 用 `DailyContext` 按 `(code, day)` 现算，盘前快照 `tdx_last_df.h5` 只做兜底（代码里有注释锁定这条）。
- 落盘原子写：`tracker.save` / `market_ctx.save` 都是 `tmp + os.replace`；影子日志有锁、每日上限、10 条一批 flush。
- 实盘隔离：**27 个提交 0 处触碰 `trading_kernel/` 与下单接口**；唯一生产接入点是 `stock_live_strategy.py` 里的只读影子钩子（异常吞掉、不改 decision）+ 主窗口一个工具条按钮。

### 3. 文档质量

每个阈值都能追到一次实测（如 `consensus_max=0.65` 对应"0~0.30 组 +2.37%、≥0.60 组 −0.33%"），模块 docstring 直接引用用户原话说明设计动机。这是本项目最值钱的资产。

## 二、本轮发现并已修复的问题

| # | 级别 | 问题 | 修复 | 效果 |
|---|---|---|---|---|
| 1 | P1 | `live_bridge.on_df` 用 `df.iterrows()` 逐行构造 Series，全市场一帧 0.67s（占 3 秒推送间隔 22%） | 改为列优先 `to_numpy()` + 下标取值；顺带修掉 **NaN 现价会被当成有效值**塞进跟踪器 | 0.67s → **0.11s**（6.4×），RSS 稳定不涨 |
| 2 | P1 | 回放热循环里的 numpy-on-scalar：`np.clip`/`np.mean`/`np.isfinite` 在 26 万~130 万次量级，占单日耗时 33%；`vanguard` 的 rank 用列表扫描（O(n)） | 新增 `_clamp/_mean_small/_clean` 标量助手 + `math.isfinite`，`_rank` 字典化，`daily_ctx` 由 8 次重复查改 1 次 | 单日 91.9s → **31.3s**（2.9×），5 日 227s → **118s**，**入局/T+1 结果逐笔一致** |
| 3 | P2 | `DayReplay` 跨日复用 tracker，但**同一天重放第二遍入局恒为 0**——阈值扫描/参数搜索会静默拿到空结果 | 记录 `_last_day`，同日重跑先重置跟踪器（跨日仍保留携带） | 幂等恢复（17 → 17），已加回归测试 |
| 4 | P2 | `on_df` 每帧 `new MarketHistory()` 读一次盘，且该实例**从未被使用** | 删掉这行无用构造 | 省掉每帧一次 JSON 读盘 |

修复后：`pytest -k fusion` **155 项全绿**（原 129 → +26），回归测试新增 NaN 现价跳过、同日重放幂等、阶段闸门三用例。

## 三、尚未解决的问题（按优先级）

1. ~~60 日回测做不了——数据是硬阻塞~~ **（已按用户纠正改写，见下）**
   用户明确指出：**不需要再叠更多分时数据，日线基座 + 最近 5 日分时已经够用；
   问题从来不是分时长度，而是"每日实盘后的上下文能力"缺失。**
   因此正确的下一步不是把分钟线加到 60 天，而是把每日上下文沉淀与自动交接建起来
   （见 `session_ctx.py` 与本文第七节第 1 条）。
   附数据事实（用于判断"能标定到什么程度"）：本地分钟线 `G:/minute_kline_cache.pkl`
   = 5576 只 × 10/19–10/23；`sina_MultiIndex_data.h5` 在 10/19 之前每天仅 16~300 行
   （自选快照，非全市场）；`tdx_all_df_300.h5` 有 36 天但每日每只仅 ~2 根。
   **权重标定仍受 5 天样本限制**，但上下文（冰点天数/饥饿度/阶段/热点/资金）
   可以靠每日沉淀无限累积——这才是可扩展的那一格。

2. **两套"可下单"口径并存**：`deploy_path`（与闸门）仍是 `live_bridge` / UI 对话框的判定口径，`ranking`（打分排序）只进了日跑与验收报告。实盘看板与日报会给出不同清单，需要明确收敛策略（建议：实盘也切到打分，`deploy_path` 降级为对照列）。

3. **阶段闸门有两个真源**：`lifecycle.PHASE_ALLOW_ENTRY` 说"先锋阵亡/退守禁止入局"，但 `tracker._advance` 实际按标签放行（先锋阵亡放排头兵/夺旗、退守现在也放）。`allow_entry` 被算出来、存进 `TrackState`，却**没有任何判定读过它**。建议二选一：删掉 `PHASE_ALLOW_ENTRY`，或让它成为唯一入口。

4. **`live_bridge` 没有生产调用方**：真实影子还没跑起来（交接单第 5 项）。on_df 应由哪个线程调用、与行情推送如何配速，均未验证。

5. **T+1 决策样本极少**：5 日只有 4 次触发（持有 2 / 减半 2），加减仓分档（交接单第 4 项）现在没有数据支撑。

## 四、性能画像（优化后，5576 只全市场）

| 路径 | 指标 | 数值 |
|---|---|---|
| `on_df` 单帧 | 冷启 / 稳态 | 1.80s / **0.11s**（最快 0.10、最慢 0.13） |
| `on_df` 内存 | 帧间 RSS | 105 → 105 MB（无泄漏） |
| `tracker.save()` | 5576 条状态 | 0.38s |
| 回放单日 | 10/19 / 10/20 | 11.9s / 31.3s（优化前 12.3 / 91.9） |
| 回放 5 日 | 总耗时 | **118s**（优化前 227s） |
| 回放内存 | 峰值 RSS | ~290 MB |
| 同日重放 | 第 2 轮 | 8.6s（缓存预热） |

**对整机的影响**：单进程峰值 ~300MB、CPU 单核打满。3 秒一帧的行情推送只占用 0.11s（3.7%），不会拖垮行情线程；但**全量 `pytest tests/` 单次运行约 12 分钟且中途被杀**（见下），建议日常只跑 `-k fusion` 或按文件分批。

## 五、回测结论（5 日闭卷，10/19–10/23）

数据上限就是 5 天，这是能给出的最强证据：

| 口径 | 笔数 | T+1 | 胜率 |
|---|---|---|---|
| 第一波入局（全部） | 198 | −0.04% | 37% |
| 与闸门（旧） | 3 | −2.07% | 0% |
| **打分排序（新，Top5/下限50）** | **22** | **+1.42%** | **47%** |

- 打分与 T+1 相关 **+0.258**：方向对，但**最高分段不可靠**（Top1 恒为 −5.01%），所以默认取前 5 分散、不押第一名。
- 阈值扫描（TopN 1/2/3/5/8 × 下限 45/50/55/60/65）**不单调**，证明权重未收敛——5 天样本标不出权重，这是预期的，也是第 1 条待办的原因。
- 盈利目标核对：22 笔组合 5 日累计 T+1 **+1.42%**（≈0.28%/日），相对全入局基准 +1.46pp。方向达成，但样本量（22 笔 / 5 日）**不足以声称策略有效**。

## 六、闭环状态

```
信号(engine) → 领先度归因(vanguard) → 战役阶段(lifecycle) → 连续判断(tracker)
   → 可下单清单(ranking) → T+1持仓决策(trap) → 复盘(panel/review/trade_sim)
```

代码链路完整，`validate_track` 已能一键跑通并落盘。**断点在三处**：

1. `live_bridge` 未接生产 → 实时链路没有影子数据；
2. T+1 决策样本 4 笔 → 加减仓分档无法标定；
3. 阶段闸门双真源（见三.3）→ 实盘与回放可能走不同分支。

## 七、结构优化建议（按优先级）

1. **每日实盘后的上下文沉淀与自动交接（已实现，见 `session_ctx.py`）**：
   - 收盘沉淀：温度曲线、宽度、阶段路径、资金量能、热点板块/轮动、先锋存活、
     入局与可下单计数、饥饿度 → `logs/fusion_state/session_ctx/<day>.json`（原子写）；
   - 自动触发：`live_bridge.on_df` 帧时间 ≥15:00 自动沉淀（每日一次），也提供显式 `close_session()`；
   - 回放同样沉淀，使离线环境可验证；
   - 缺失重建：快照不在时用日线基座 + 5 日分时重建，`source="rebuilt"` 可区分，缺失项进 `missing`；
   - 交接：`handoff()` / `render_handoff()` 给次日盘前"最近 N 日上下文"，日报已带该摘要。
   **这是用户指定的架构主线**："每次自动更新迭代交接，才能反复验证有效性"。
2. **实盘切到打分口径**：`live_bridge`/UI 用 `rank_entries` 出清单，`deploy_path` 留作对照列；同时删掉 `PHASE_ALLOW_ENTRY` 或让它成为唯一阶段闸门。
3. **跑通真实影子**：把 `on_df` 接到行情回调，先用 `logs/fusion_state/` 落盘核对字段映射与帧率，再谈信号质量。
4. **加减仓分档**：等上下文积累 + 影子数据齐了再做，现在做就是再次过拟合。
5. **测试分层**：把需要 G: 盘全市场数据的测试标成 `@pytest.mark.slow`，日常只跑快集；全量测试单独夜间跑。
