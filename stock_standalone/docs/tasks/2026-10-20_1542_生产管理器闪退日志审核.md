## 主要发现

1. **P1：Qt 致命消息缺少可靠文件落点。** `sys_utils.py:44` 的消息处理器直接 `sys.stderr.write`，未接入 `WindowManager` 文件日志；`manage_window_layout.spec` 为 `console=False`。stderr 为 None 时该处理器自身可能报错，桥输出路由存在时主线程又可能因空 fallback 丢弃输出（`desktop_bridge_thread_output.py:105`）。这是真实诊断缺陷，尚不是本次闪退已证实根因。
2. **P1：未发现管理器级未捕获异常和原生崩溃记录。** 启动入口、UI 与桥范围内没有统一 `sys.excepthook`、`threading.excepthook`、`faulthandler` 落盘接线；日志初始化位于 UI 模块导入期间，早期导入异常也可能不入主日志。子线程业务日志不能替代主线程或原生崩溃堆栈。
3. **P1：退出生命周期没有可审计标记。** `ui.py:4195` 正常退出、`ui.py:8065` 的 aboutToQuit 清理及 `ui.py:8215` 事件循环返回没有统一记录退出来源、PID、返回码和清理结果；旧进程退出码未留存，无法区分主动退出、未捕获异常和外部终止。
4. **P2：主日志无轮转，且文件初始化失败仅写 stderr。** `ui.py:212` 使用普通 FileHandler，缺乏大小/保留周期限制；初始化失败的提示在隐藏模式也可能不可见。当前 3.8 MB 不足以认定为本次闪退原因。
5. **风险边界：双桥运行在管理器进程内。** Python 常规桥错误通常被现有包装降级，但任一同进程原生故障仍可能带走整个管理器；新增独立桌面启动含 ctypes 调用，也必须纳入 dump 定位范围，不能仅凭之前 5 分钟验收排除。没有证据将本次归因于 AGY、静态路由、Acer 或 RamDisk。

## 建议修复顺序（本次未实施）

1. 仅为管理器建立启动早期诊断文件，覆盖 Python 主/子线程未捕获异常、Qt Critical/Fatal、faulthandler；Qt 回调应避免递归日志与 stderr 空值，不将致命故障伪装成正常继续。
2. 增加进程启动/退出标记（完整日期、PID、版本/哈希、启动模式、退出来源/返回码），以及主日志轮转；避免记录提示词、账号或密钥。
3. 在隔离测试进程验证主线程异常、后台异常、Qt 致命错误、原生异常及正常退出的落盘区别；禁止对生产管理器注入崩溃来验收。
4. 若 Python 堆栈仍不足，再单独为管理器配置转储捕获并取得下一次现场退出证据；本次未修改 Windows 注册表或 WER 配置。
