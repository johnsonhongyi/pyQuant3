# 全系统联动持续迭代方案

## 结论

- 当前为条件通过：已完成本轮桌面联动关键路径复审并修复已定位问题；不等于 Go/Web/ATS 所有功能已完成全面验收。
- 已打包版本留作用户下一交易时段实盘观察基线；本轮仅改后续源码，没有重新打包、部署、调整交易规则或写生产数据。
- 保留工作区原有六位代码修复与 nuitka-crash-report.xml 改动，不覆盖用户文件。

## 本轮已实施

| 路径 | 原问题 | 当前处理 |
|---|---|---|
| Context 调度 | 关注同步设有 5 秒截止时间，但等待仍可能到 60 秒 | 关注与上下文按各自截止时间等待；网络耗时仍可能推迟实际执行 |
| 状态展示 | 中途关注/上传状态变化不通知；上下文失败覆盖已有同步状态 | 状态变化即时通知，错误状态保留 attention/publish |
| Tk 队列 | 多次共享上下文通知排入多个过时任务 | 最多保留一个待消费任务，覆盖为最新快照；六位代码入口保持 |
| 证据上传 | 单轮最多十次串行请求阻塞同线程其他同步 | 单轮上传一条，余下记录仍留可靠 outbox，不丢弃 |
| Gateway 回执 | 128 条待确认回执触发连续自唤醒 | 消费者未确认时按定时轮次重试，真实指令积压仍继续处理 |
| Context 生命周期 | stop 超时仍清空线程引用，start 可再建线程 | 未退出线程保留引用，停止中的线程不再报告启动成功 |

## 当前机制复核

- StockSender 使用单个最新待发送任务，补充行情单请求后台处理；关注版本/交易日校验仍保留。
- Context 网络有 8 秒请求超时和 8 MiB 响应上限；网关客户端并发受信号量限制。
- 当前 linkage_storage 已有 RAMDisk 缺失显式失败、100 MiB 数据库上限、事件条数/字节裁剪、归档窗口和跨进程写锁。旧文档中“无限增长/静默磁盘回退”的结论不能直接沿用于当前源码。
- 指令幂等记录、关注来源、删除墓碑和未完成 outbox 的恢复契约保持；不采用清空数据库换取速度的方案。

## 后续实施顺序

1. **P1：慢网公平性与退出。** 当前单次上传或 attention 请求仍可占用轮询线程数秒；stop 仍有同步 drain 持久化路径。下一步核验写入所有权、超时退出和出站证据交接，再决定独立网络任务，不直接增加并发写者。
2. **P1：端到端关注收敛。** 对照当前 Go/Web/ATS 源码，复核同源地址、批量幂等重放、删除墓碑优先级、晚到回执和跨节点证据结构。仅隔离数据验证关键分支，不重放真实生产指令。
3. **P2：点击成本。** summary_for_symbol 与事件摘要仍遍历题材成员和证据；评估按后台快照建立符号索引。避免缓存最终 freshness 文本而把过期信息伪装为实时。
4. **P2：联动状态可解释。** 基于现有状态开发轻量详情：来源交易日、最后成功同步时间、错误原因、待上传/待回执数量。数据随后台状态变更发布，禁止新增 UI 定时全表扫描。
5. **P2：重试与人工恢复。** 为失败操作提供明确的只读原因和可审阅重试入口；重试继续复用幂等标识，不把 accepted 当成所有消费者已生效。
6. **发布门禁。** 根据用户实盘反馈核对主行情延迟、竞价刷新、语音中断恢复和联动确认；达到明确闭环再打下一版，避免混淆包版本与源码版本。
