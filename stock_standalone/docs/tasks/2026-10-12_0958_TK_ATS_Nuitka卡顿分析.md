## 早盘 90 秒规则的准确含义

- `data_utils.py:3880`：`918 < HHMM < 926 or 929 < HHMM < 945`，对应 09:19～09:25、09:30～09:44；不是完整的 09:15～09:45 区间。
- 本次生产 `duration_sleep_time=180`；实际一轮周期还包含取数、计算和交付时间，也可能因状态变化提前结束休眠。
- `ActualSleep` 日志在减半语句之前打印，可能显示 180 秒而随后实际休眠 90 秒；日志标签有误导性。
- 09:45:40 与 09:48:47 两次已记录的视图慢回调相隔约 187 秒，符合恢复 180 秒休眠后的节奏；这不是所有行情交付的完整计数。
- 已经开始的一轮 90 秒休眠不会在 09:45 整自动改成 180 秒，规则在选择下一轮休眠时生效。

## CPU、进程与系统资源

- 一次约 09:43 的 8 秒采样：TK 主进程 28316 为 162.89%，ATS 主进程 30352 为 116.8%，ATS 子进程 25340 为 62.5%；CPU 百分比按单核心计算，机器有 12 个逻辑核心。
- TK 最热线程约 83.2% 单核心；主 GUI 线程 31348 约 38.28%。ATS 主 GUI 线程 33724 约 41.02%，说明界面线程本身也在消耗显著 CPU。
- 同次系统 CPU 46.9%、内存占用 73.1%；采样没有捕获用户观察到的全系统 CPU 100% 峰值，不能用恢复后的采样否定现场。
- 另一时段 Defender、通达信、Explorer 也有明显 CPU 消耗；没有证据把它们判定为 TK 冻结的唯一原因。
- 物理磁盘读取约 0.04 MB/s；TK 的进程 I/O 读取较高不能直接等同于物理磁盘瓶颈。
- TK 的 GDI/USER 资源约 174/301，ATS 173/143，SBC 153/110；当前没有句柄配额耗尽证据。
- Nuitka 单文件父进程、解压后的主进程和 `--multiprocessing-fork` 子进程同时存在，属于可解释的进程结构，不能仅凭同名 exe 多个就认定重复启动。

## 其他风险与证据边界

- TK 的心跳路径仍会同步调用 `find_ipo_detector_window -> EnumWindows`；历史阻塞堆栈出现过此路径，本次尚未直接确认。已有后台窗口扫描不代表所有发现窗口的调用都已异步化。
- Tk 驱动的 Qt `sendPostedEvents()` 也可能执行耗时 Qt 回调；竞价恢复与 GUI 线程重新空闲一致，但没有逐个 Qt slot 的耗时证据。
- 点击股票会触发选择联动；右键菜单弹出前也有选择、剪贴板等操作，单次现场没有精确打点。菜单尚未出现、删除命令尚未执行，不能归咎于“删除关注”的持久化写入。
- `StockSender.send` 已使用后台发送队列，不能把这处发送直接当作 UI 同步网络阻塞。
- ATS 的 `refresh_realtime_ui`、`_on_ledger_results` 仍在 UI 线程更新多个面板；有 CPU 证据但缺少本次回调计时，ATS 热子进程的具体工作角色也尚未确认。
- 当前权限下窗口枚举未返回目标桌面 HWND，未取得 Ghost 窗口身份；只凭截图无法确认图标变化和缩略图移位的具体路径。
- Windows 会为数秒不处理消息的顶层窗口创建 Ghost 替代窗口；与本次任务栏异常相符，但属于解释假设，不能作为独立根因结论。
- 官方依据：[Microsoft：About Messages and Message Queues](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-messages-and-message-queues)。

## 建议的最小修复顺序

1. 将关注行情标准化、合并和排序放到后台；一次建立代码索引，批量合并，UI 只应用最新版本差异；保持现有 freshness、来源和交易日字段契约。
2. 保留值缓存，仅更新实际变化的行；Top10 数据准备后台化，Tk 操作按短时间预算分片，顺序不变时跳过 `move`。
3. 后台完成回调只交付结果；减少 UI 上的全表复制、指纹计算和重复选择事件。以最慢回调而不是仅队列长度衡量响应性。
4. 窗口发现统一读取后台缓存；保留 Windows 下 Qt 事件泵的既有安全约束，不贸然替换为嵌套 `processEvents()`。
5. 再为 ATS 面板更新和热子进程增加有界计时；修正休眠日志打印位置，使日志显示真正选定的间隔。
