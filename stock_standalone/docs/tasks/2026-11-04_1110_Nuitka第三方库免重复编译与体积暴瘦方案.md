# Nuitka 第三方库免重复 C 编译与体积暴瘦优化方案

日期：2026-11-04 11:10
执行人：高级全栈开发专家

## 1. 核心问题定位与深度审计
用户明确指示：“现在修复的是 nuitka 打包远大于 pyinstaller 的问题，小包无所谓，不必浪费这么大精力”。

通过对真实构建产物 `build\run_ats.dist` 进行物理深度扫描，查出三大核心事实：
1. **多出的 160MB 100% 集中在主程序单体**：
   - 依赖的第三方 DLL（`openblas` 34MB, `Qt6` 21MB, `python39` 4MB 等）及数据文件加起来才 ~88MB，与 PyInstaller 完全一致；
   - 唯一的巨型膨胀点在于：单个 `ATS_Terminal.exe` 高达 **173.47 MB**（占解压总目录的 66.2%），而 PyInstaller 对应主引导程序仅 **500 KB**。
2. **1674 个模块被无差别转译为 C 代码**：
   - `pandas`：258 个模块被转译为 C 代码；
   - `openpyxl`：176 个模块被转译为 C 代码；
   - `pandas_ta`：162 个模块；
   - `pyqtgraph`：128 个模块；
   - `numpy`：92 个模块；
   - `tushare`、`pytdx`、`aiohttp`、`requests`、`urllib3`、`chardet` 等 400 多个模块全部转译为 C 代码；
3. **90% 以上的模块 C 转译毫无价值甚至属于负优化**：
   - `numpy`、`pandas`、`PyQt6`、`tables` 底层早已是 `libopenblas.dll`、`algos.pyd`、`QtWidgets.pyd` 等 C/C++ 极速扩展，Python 层只是薄薄的接口胶水，转译为 C 机器码没有任何性能收益，却带来 20~30 倍的代码体积膨胀；
   - `openpyxl`、`aiohttp`、`requests`、`chardet` 纯属 I/O 密集型或辅助模块，根本不走量化实时高频计算路径；
   - 真正需要且唯一需要 C 原生编译加速与源码保护的，仅有本工程内部的 **`ats`（~200 个模块）与核心策略算法**！

## 2. 解决方案：NuitkaSmartOptimizerPlugin 智能插件
基于 Nuitka 官方提供的 `--user-plugin` 机制与 `decideCompilation` 钩子，开发了专用编译路由插件 [tools/nuitka_smart_optimizer_plugin.py](file:///d:/MacTools/WorkFile/WorkSpace/pyQuant3/stock_standalone/tools/nuitka_smart_optimizer_plugin.py)：

- **精准自动分流**：
  1. **本地业务代码（工程工作区内）** $\rightarrow$ 返回 `"compiled"`：全量编译为 C 原生机器码，确保毫秒级实时计算性能与 100% 策略防反编译。
  2. **第三方依赖库（`site-packages` / 外部库）** $\rightarrow$ 返回 `"bytecode"`：保留为标准的 Python 字节码由内置解释器直接加载。
- **全链路构建接入**：
  在以下三个打包批处理脚本中注入 `--user-plugin="%~dp0tools\nuitka_smart_optimizer_plugin.py"` 与 `--no-deployment-flag=excluded-module-usage`：
  - `nuitka_build_ats_console_onlyClang.bat`
  - `nuitka_build_console_onlyClang.bat`
  - `nuitka_build_multi_period_dialog_onlyClang.bat`

## 3. 预期收益评估
1. **编译模块数量**：从 1674 个暴降至 ~200 个（减少 ~88%）；
2. **编译与链接耗时**：从 20~40 分钟直接缩短至 **3~5 分钟**；
3. **主 EXE 二进制体积**：预计削减 **70 MB ~ 100 MB**，整体产物向 PyInstaller 靠拢；
4. **运行稳定性**：彻底阻断第三方库（如 `pyqtgraph`、`pandas`、`requests`）因 Nuitka C 转译导致的怪异底层兼容性报错。
