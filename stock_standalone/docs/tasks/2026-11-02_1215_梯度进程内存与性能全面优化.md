# 2026-11-02 12:15 梯度进程内存与性能全面优化

## 一、现象

- 交易时段 ATS_Terminal（梯度独立进程）单核长期 100%，界面与梯度看板持续卡顿。
- 该进程私有提交 **8,756 MB**、工作集 8,336 MB（物理内存 32 GB，可用仅 3.1 GB）。
- 午休（影子文件停止增长）时内存持平（8,757 → 8,273 MB），说明不是无条件慢泄漏，
  而是交易时段刷新循环造成的驻留与碎片。

## 三、根因链

1. **写入端膨胀**：11-01 17:25 `085f77c3` 接入策略观察证据后，`stock_live_strategy.py:3196`
   对每个观察候选每轮采样都写一条带 4.4 KB 证据的记录，记录数 8.3×、单条 2.7×。
2. **读取端全量重解析**：`shadow_io.read_paths` 每次把整份分片读成 list，并对每条记录
   再做一次 `json.dumps(sort_keys=True)` 生成去重指纹（占单次耗时 6.25 s / 12.64 s）。
3. **缓存必然失效 + 多份副本**：`load_live_rows` / `load_live_series` 以「文件大小+修改时间」
   为缓存键，而交易时段文件每几秒追加 → 键必变 → 缓存必失效；两者各存最多 8~12 份
   全量副本（`_LIVE_ROWS_CACHE` / `_LIVE_SERIES_CACHE`）。
4. **UI 线程同步执行**：`_live_timer.start(2000)` → `_auto_refresh_live` → `_render_live`
   在 GUI 线程里同步跑上述读取，每 2 秒要完成约 13.5 秒的活 → 单核打满、界面卡死。

## 七、第二轮：数据结构重构（极限内存）

第一轮解决"读得慢"，第二轮解决"存得胖"。逐字段实测（3,000 条真实记录，tracemalloc）：

| 字段 | 单条字节 | 占完整记录 |
|---|---|---|
| 完整记录 | 37.3 KB | 100% |
| `observation_evidence` | 19.1 KB | **51%** |
| `track` | 3.8 KB | 10% |
| `struct` | 1.2 KB | 3% |
| 去掉全部重字段后 | 11.6 KB | 31% |

根因不止是字段大：`fusion` 字典 JSON 只有 566 字节，常驻却占 4,513 字节（8 倍），
因为每条记录的 80~100 个键字符串都是 `json.loads` 逐条重建的。

### 三项改造

1. **键与短字符串驻留**（`intern_tree` / `_compact_value`）：所有记录共享同一份键。
   单条 37.3 KB → 20.7 KB（-44%）。用 `type()` 派发而非 `isinstance`，避免遍历变慢。
2. **热/冷字段分离**（`COLD_FIELDS` + `compact_record` + `hydrate`）：
   `observation_evidence / track / reclaim_detail / legacy` 移出常驻，只留
   `(path, offset, length)`；tooltip 或赛马入口需要时按偏移回读原文。
   实测水合后与原行**逐字段一致**。
3. **派生值兜底**：跨日汇总（`cross_day.py`）原本逐条读证据与跟踪阶段，改为在精简时
   预存两个极小派生值 `_evidence_reason` / `_track_stage`，避免为判定而回读 3 万次文件。

### 第二轮实测

## 九、第三轮：三个遗留点的处理

### 1. `fusion` 字典 8 倍膨胀 —— 已修复，可验证

修复方式见第八节（键与短字符串驻留）。复核证据：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `fusion` 单条常驻（tracemalloc，3,000 条） | 4,613 B | **3,124 B（-32%）** |
| 两条记录的同名键是否同一对象 | 否 | **是（`k is kk` 为 True）** |
| 完整记录单条 | 37.3 KB | **6.5 KB（-83%）** |

剩余的 3,124 B 已不是"重复字符串"，而是 22 个小键的 Python dict 表开销 + 值本身
（JSON 566 B 的 5.5 倍是 CPython 容器的固有成本）。要再往下只能把记录换成列式/元组
存储，会牵动 200 多处按名取值的调用点，收益不抵风险，本轮不做。

### 2. 表格重建 —— 改为 30 秒 + 行集指纹 + 关闭重绘

- `_live_timer` 周期 **2 s → 30 s**。看板展示的是"每票最新一条"，该行集通常几分钟才变。
- 新增 `_rows_fingerprint()`：按 `(code, ts, tier, rar, focus_rank)` 生成行集指纹，
  与上次渲染相同则**直接返回，不重建表格**（文件追加但行集没变时零成本）。
- `_render_live` 拆成包装层 + `_render_live_inner`，包装层用
  `setUpdatesEnabled(False)` + `try/finally` 包住整表重建，避免 3.3 万个单元格逐个触发重绘。

### 3. `strategy_observation` 降采样 —— 阶梯步点保留，重复状态丢弃

按"记录上一次状态即可"落地，口径写进 `ats/fusion/shadow.py`：

1. **结构状态 / 确认次数 / 级别 / 观察结论** 任一变化 → 立刻落一条（阶梯的每一级都在）；
2. 状态没变时，只有**曾经激活**（有观察结论或级别≥2）的标的按心跳留价格锚点，
   保证入局后 MFE/MAE 连续；
3. 从未激活且状态未变的票不落盘（其价格序列没有下游用途）。

配置：`observation_state_heartbeat_s`（默认 600 秒，下限 60）。

用今日 33,245 条真实记录回放不同口径：

| 口径 | 保留条数 | 占比 | 文件估算 |
|---|---|---|---|
| 现状（每轮采样都写） | 33,245 | 100% | 222 MB |
| 状态变化 + 全量心跳 600 s | 11,946 | 36% | 80 MB |
| **状态变化 + 仅激活票心跳 600 s** | **6,009** | **18%** | **40 MB** |

阶梯步点（状态变化）一条不少，重复状态压掉 82%。

## 十一、遗留与决策点

1. **必须重新打包才生效**：线上 `<INSTALL_DIR>\instockMonitorTK\ATS_Terminal.exe`
   （11-02 00:00 构建）与 `instock_MonitorTK_Nuita.exe`（11-01 20:43）仍是旧代码。
2. **表格重建已收敛**：30 秒周期 + 行集指纹跳过 + 关闭重绘。若后续仍嫌刷新慢，
   可把 `_render_live_inner` 改成按行 diff 更新（保留 QTableWidgetItem），但改动面大。
3. **记录频次已收敛（第三轮）**：观察源只在状态变化时写，已激活标的按 10 分钟心跳补锚点，
   实测压掉 82%。若还要更稀，调 `observation_state_heartbeat_s` 即可，无需改代码。
4. **首次加载仍有 7.1 s**：222 MB 病态分片的一次性代价（正常 10 MB 分片约 0.3 s）。写入端
   瘦身（-14.7%）与频次收敛后会自然回落；若仍需更快，只能改成分片预索引。
5. **内存下限**：单条 6.5 KB 已是"热字段 + 驻留字符串"的真实下限。要再降只有两条路——
   调低 `fusion_shadow_retention_records`（2 万→1 万约省 63 MB），或把热字段也改成列式存储。
6. **今日 11-02 分片仍为 222 MB 旧格式**，新代码读取无碍（增量游标兼容），但瘦身只对
   新写入记录生效。
