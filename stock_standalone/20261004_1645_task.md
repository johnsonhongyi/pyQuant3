# 全面排查与彻底关闭打包脚本未授权Clean操作与自动清理缓存专项任务

## 任务背景与核心要求
- **用户指令 1**：查询打包的脚本有没有在未经我许可就进行 clean 的操作，全面关闭；
- **用户指令 2**：之前有个自动打包脚本似乎会每次都清理缓存，找到并关闭这个设置。

---

## 溯源调查与根本原因剖析

通过对历史对话记录（`transcript.jsonl`）、工程现有构建批处理脚本（`*.bat` / `*.cmd`）及辅助 Python 脚本进行地毯式静态审查与代码穿透，查明导致“缓存被清空”、“打包速度极慢”以及“存在未经许可 clean 操作”的四大真实根因：

### 1. 历史自动打包脚本 `build.bat` 的暴力删除逻辑（已捕获并关闭）
- **根因位置**：`stock_standalone/build.bat:29-30`
- **原代码逻辑**：
  ```cmd
  echo [步骤 1] 清理旧的构建文件...
  if exist "%DIST_DIR%" rmdir /s /q "%DIST_DIR%"
  if exist "%BUILD_DIR%" rmdir /s /q "%BUILD_DIR%"
  echo [完成] 旧文件已清理
  ```
- **严重后果**：只要运行 `build.bat`，它会在打包伊始无条件执行 `rmdir /s /q "%BUILD_DIR%"`，直接把工程根目录下积累的数 GB 模块依赖分析中间目录、Scons 中间缓存和已有构建产物全部抹除，强制每次构建退化为 20 分钟全量冷构建。
- **加固动作**：将 `rmdir` 彻底注释禁用，改为“保留已有构建缓存 (按用户指令已全面关闭自动清理)”。

### 2. `nuitka_build_ats_console_onlyClang.bat` 误加 `--remove-output` 导致每次清空中间 C 源码（已捕获并关闭）
- **根因位置**：`stock_standalone/nuitka_build_ats_console_onlyClang.bat:228`
- **对比排查**：
  - 用户反馈“原有代码逻辑 tk 的 nuitka 已经稳定运行”，经对比发现 `nuitka_build_console_onlyClang.bat`（TK 脚本）中**完全没有** `--remove-output`；
  - 而 ATS 脚本中在 Nuitka 参数末尾被硬编码了 `--remove-output`！
- **严重后果**：Nuitka 官方参数 `--remove-output` 的定义为构建成功后清空生成的所有 C 源码、对象文件及中间目录。这导致 ATS 每次打包完成后，下一轮构建完全没有上一轮的中间源码可以比对复用，导致构建时间飙升至 22 分钟以上。
- **加固动作**：彻底删除 ATS 构建脚本及 `nuitka_instockMonitor.bat`、`test_build.bat` 中的 `--remove-output` 参数，恢复增量源码保留机制。

### 3. `tools/archive_build_exe.py` 构建前后静默执行版本过期清理（已捕获并关闭）
- **根因位置**：`stock_standalone/tools/archive_build_exe.py:256, 270`
- **原代码逻辑**：在 `pre-build` 与 `post-build` 阶段，自动调用 `clean_expired_archives` 将超过 7 天的历史版本静默删除。
- **违规性质**：违反用户“未经许可不得执行任何 clean 操作”的铁律。
- **加固动作**：
  - 打包前/打包后阶段彻底切断 `clean_expired_archives` 调用，仅对保留的历史版本进行增量归档与列表统计呈现；
  - 严格限制：历史清理只有在显式传入 `--stage clean-only` 时才允许执行。

### 4. 历史助手会话误触 `clean_nuitka_cache.bat -y` 溯源确认
- **根因位置**：2026-10-03 09:58 对话流中，开发调试 `clean_nuitka_cache.bat` 时，前序助手执行了 `cmd.exe /c clean_nuitka_cache.bat -y`，清空了 `.nuitka_cache` 与相关缓存，造成用户感知到“缓存突然被清空了”。
- **加固动作**：
  - 设立绝对红线：任何代理助手与自动化脚本严禁在后台或非显式交互下调用 `clean_nuitka_cache.bat`；
  - `instock-nuitka-batch.cmd` 中将 clean 仅作为 `[6]` 手动入口，默认回车严格运行 `1` (ats)，绝不触发 clean；且进入 `[6]` 后必须由用户在终端二次输入 `[Y/n]` 确认。
